# Review Opale — sécurité, dépendances, architecture

*Revue de code externe, juillet 2026 — commit `6cbc9ea`.*

Portée : `api/` (237 fichiers, 150 routes), `front/` (~1,2 Mo de JS vanilla),
`agent-go/` (71 fichiers), `cli/`, chaîne de build/déploiement (Docker, CI,
installeur one-liner).

---

## 0. Résumé exécutif

Opale est un projet nettement au-dessus de la moyenne des RMM auto-hébergés sur
plusieurs points précis : la chaîne de mise à jour de l'agent (ed25519 + SHA-256
+ pinning SPKI + rollback) est correcte, le module `ask` (LLM → SQL) est conçu
avec la bonne frontière de sécurité, les grants one-shot pour les WebSockets SSH
et console sont un vrai bon pattern, le SQL est paramétré quasi partout, et le
front dispose d'un helper `esc()` appliqué avec discipline. La densité de
commentaires expliquant *pourquoi* est remarquable et facilite l'audit.

Les problèmes réels sont concentrés ailleurs : **le modèle d'autorisation**
(un seul booléen `is_admin`, et des routes sensibles laissées en
`authenticate` seul), **la posture de déploiement** (conteneur root, image
non reproductible, vendors CDN non épinglés, Node 20 EOL) et surtout
**l'absence de runner de migrations**, qui rend l'installation documentée
non fonctionnelle et chaque montée de version manuelle et risquée.

Classement par gravité :

| # | Problème | Gravité |
|---|---|---|
| 1 | Migrations 002→070 jamais appliquées par l'installeur → instance cassée | **Critique** (fonctionnel) |
| 2 | Routes sensibles ouvertes à tout utilisateur authentifié du tenant | **Élevée** |
| 3 | Aucune vérification de clé d'hôte SSH (`hostVerifier` absent) | **Élevée** |
| 4 | Conteneur API en root + concentration de tous les secrets | **Élevée** |
| 5 | Vendors front téléchargés du CDN sans SRI ni pin de version | **Élevée** |
| 6 | `npm install` sans lockfile dans l'image + Node 20 EOL | **Moyenne-élevée** |
| 7 | SSRF + exfiltration de clé API via `ask.url` / URLs LLM en settings | **Moyenne** |
| 8 | `POST /api/agent/setup-log` non authentifié → pollution de l'audit | **Moyenne** |
| 9 | Bootstrap token : revendication d'un hostname arbitraire, token perso sans expiration | **Moyenne** |
| 10 | Absence d'en-têtes de sécurité / CSP réelle + tokens MSAL en `localStorage` | **Moyenne** |
| 11 | Boucles non bornées (checkin, `Promise.all` SSH, buffers mémoire) | **Moyenne** |
| 12 | Pas de linter, pas de SAST, pas d'audit de dépendances en CI | **Moyenne** |
| 13 | Duplication intégrale desktop/mobile (19 vues × 2) | **Moyenne** (évolutivité) |
| 14 | `winget-index` : ~50 Mo de MSIX + SQLite résidente dans le process API | **Moyenne** (robustesse) |
| 15 | Validation d'entrée quasi absente (7 schémas Fastify sur 150 routes) | **Faible-moyenne** |
| 16 | Divers : lockout admin, WebAuthn décoratif, branding en dur, dette documentée | **Faible** |

## 1. Critique — l'installation documentée produit une instance cassée

C'est le point le plus important du rapport, et ce n'est même pas un problème de
sécurité : c'est un problème de correction.

`api/migrations/MIGRATIONS.md` l'assume explicitement :

> `002+` : appliquées **manuellement** par le maintainer après rebuild/déploiement.
> Il n'existe **pas** de table `_migrations` ni de runner intégré.

Or `docker-compose.yml` et `docker-compose.example.yml` ne montent que
`001_init.sql` dans `/docker-entrypoint-initdb.d/`, et `landing/install.sh`
(le `curl … | bash` mis en avant dans le README) fait un `git clone` +
`docker compose up -d` et rien d'autre.

Les chiffres :

- 62 fichiers de migration, dont **61 non appliqués** par le chemin d'install nominal ;
- 45 tables créées au total dans l'historique, dont **16 seulement dans `001_init.sql`**.

Manquent donc, sur une installation neuve : `packages`, `deployments`,
`remote_sessions`, `remote_session_logs`, `cli_tokens`, `ticket_attachments`,
`device_admin_credentials` (LAPS), `push_subscriptions`, `settings`,
`compliance_results`, `user_prefs`, tout l'email-bridge… soit la quasi-totalité
des fonctionnalités annoncées dans le README.

L'installeur affiche par ailleurs :

> Your account becomes the first admin automatically.

Ce n'est pas ce que fait le code. `POST /api/users/sync-me`
(`api/modules/core/routes/users.js:74`) fait un simple upsert et lit `is_admin`,
qui vaut `DEFAULT false` (`001_init.sql:9`). Aucun bootstrap premier-admin
n'existe. Sur une instance neuve, **personne n'est admin** et il faut un
`UPDATE users_cache SET is_admin = true` en psql pour débloquer.

**Ce qu'il faut faire.** C'est le chantier prioritaire, avant toute autre chose :

1. Un runner de migrations en Node exécuté au boot de l'API — table
   `schema_migrations (version, applied_at, checksum)`, advisory lock Postgres
   (`pg_advisory_lock`) pour sérialiser plusieurs instances, application dans une
   transaction par fichier, refus de démarrer si une migration déjà appliquée a
   changé de checksum. ~150 lignes, et ça supprime toute une classe d'incidents
   de déploiement.
2. Un bootstrap premier-admin explicite : si `SELECT count(*) FROM users_cache
   WHERE is_admin` = 0, le premier `sync-me` promeut — avec un log d'audit
   dédié — ou, plus sûr, une variable `OPALE_BOOTSTRAP_ADMIN_UPN` comparée à
   l'UPN du token.
3. Un endpoint `GET /health` retournant la version de schéma appliquée, et un
   `healthcheck:` sur le service `api` dans les deux compose (il n'y en a que
   sur `db` aujourd'hui).

## 2. Élevée — le modèle d'autorisation n'a qu'un seul cran

L'autorisation repose entièrement sur un booléen `users_cache.is_admin`. Il n'y
a ni rôles, ni scopes, ni séparation lecture/écriture. Conséquence directe :
**tout utilisateur du tenant Entra qui obtient un token valide** — donc toute
personne de l'organisation, pas seulement l'équipe IT — accède aux routes
protégées par `fastify.authenticate` seul.

Comptage : sur 150 routes, une trentaine sont en `authenticate` sans
`requireAdmin`. Les plus significatives :

| Route | Effet |
|---|---|
| `GET /api/devices` (`devices.js:18`) | Inventaire complet du parc : hostnames, serials, OS, taux de remplissage disque, **IP Netbird**, utilisateur assigné |
| `POST /api/packages` (`packages.js:56`) | Création d'un package avec `install_script` PowerShell arbitraire |
| `PATCH /api/packages/:id` (`packages.js:206`) | Modification de l'`install_script` de n'importe quel package |
| `DELETE /api/packages/:id` (`packages.js:239`) | Suppression de n'importe quel package |
| `GET /api/users/search` (`users.js:190`) | Annuaire complet (nom, e-mail, fonction) |
| `POST/PATCH/DELETE /api/stock/*` | Écriture sur tout l'inventaire matériel |
| `GET /api/rapports` | Agrégats, coûts, activité |

Le garde-fou sur les packages est le gate d'approbation : `deploy` exige
`status = 'approved'` et un `PATCH` sur un package approuvé le repasse en
`draft` (`packages.js:213`). C'est un bon réflexe, mais il est **incomplet** :
l'approbation ne lie pas le contenu revu. Un utilisateur non-admin peut modifier
l'`install_script` d'un package encore en `draft` entre le moment où l'admin le
relit dans l'UI et le moment où il clique « Approuver » — le `PATCH` ne
déclenche alors aucun retour en `draft` puisque le statut n'était pas
`approved`. L'admin approuve un contenu qu'il n'a pas vu, et ce contenu part
en SYSTEM sur le parc.

Par ailleurs, `PATCH /api/tickets/:id` (`tickets.js:402`) écrit `status` et
`priority` sans validation d'énumération côté serveur, et il n'existe aucune
contrainte `CHECK` sur ces colonnes (`001_init.sql:63-64`) — contrairement aux
tables plus récentes (`041`, `048`) qui, elles, en ont. On peut écrire un statut
arbitraire et casser silencieusement le rendu Kanban.

**Ce qu'il faut faire.**

- Passer les écritures `packages` et `stock` en `requireAdmin`, et restreindre
  `GET /api/devices` (soit `requireAdmin`, soit un scope « mes postes » via
  `assigned_user_id`).
- Lier l'approbation au contenu : stocker `approved_content_sha256` au moment de
  l'approbation, et le revérifier au `deploy`. Trois lignes, et le gate devient
  réel.
- Ajouter des `CHECK` sur `tickets.status` / `tickets.priority`, et valider les
  énumérations à la frontière HTTP.
- À moyen terme, introduire un vrai modèle de rôles (`viewer` / `technician` /
  `admin`). Le booléen unique est déjà l'obstacle structurel à toute évolution
  du produit vers du multi-équipe.

## 3. Élevée — SSH sans vérification de clé d'hôte

`api/modules/remote/routes/ssh.js:184` et
`api/modules/inventory/routes/scripts.js:55` appellent `conn.connect()` de
`ssh2` sans fournir de `hostVerifier` :

```js
conn.connect({
  host:       device.ip_netbird,
  port:       parseInt(process.env.SSH_PORT || '22', 10),
  username:   process.env.SSH_USER || 'opale',
  privateKey: sshKey(),
  readyTimeout: 10_000
})
```

Sans `hostVerifier`, `ssh2` accepte n'importe quelle clé d'hôte. Il n'y a aucun
`known_hosts` côté serveur.

L'authentification par clé publique empêche un attaquant de rejouer la clé
privée d'Opale, mais elle ne l'empêche pas de **se faire passer pour le poste
cible**. Quelqu'un capable de détourner le trafic vers l'IP Netbird — un nœud
du mesh compromis, un poste dont l'IP est réattribuée, un `ip_netbird` altéré
en base — obtient :

- le contenu intégral des scripts PowerShell exécutés (`conn.exec(scriptCode)`),
  qui contiennent en pratique des identifiants d'installation ;
- tout ce que l'admin tape dans le terminal web, mots de passe compris ;
- la capacité de renvoyer une sortie falsifiée, donc de faire croire à une
  remédiation qui n'a pas eu lieu.

Le mesh VPN est traité comme un périmètre de confiance, ce qui est exactement
l'hypothèse que le modèle zero-trust invite à ne pas faire — et le README
recommande précisément Netbird/Tailscale/ZeroTier, des réseaux où les IP sont
réattribuables.

**Ce qu'il faut faire.** Persister l'empreinte de clé d'hôte au premier contact
(TOFU) dans une colonne `devices.ssh_host_key_sha256`, et passer un
`hostVerifier` qui la compare. Le premier enrôlement peut se faire au moment du
déploiement de la clé publique. Épingler aussi `algorithms` pour éviter une
négociation vers des primitives faibles.

## 4. Élevée — le conteneur API concentre tous les secrets et tourne en root

Ni `Dockerfile` ni `api/Dockerfile` ne contiennent de directive `USER`. Le
process Node tourne donc en **root** dans le conteneur. Et ce conteneur détient,
simultanément :

- `agent-go/keys/signing.key` — la clé de signature ed25519 des binaires agent ;
- `agent-go/keys/laps.key` — la clé RSA de déchiffrement des mots de passe
  administrateur local de tout le parc ;
- `SSH_PRIVATE_KEY_B64` — la clé SSH donnant accès à tous les postes ;
- `ENTRA_CLIENT_SECRET` — permissions applicatives Graph
  (`User.Read.All`, `Device*`, `Mail.ReadWrite`, `Mail.Send`, `GroupMember.Read.All`) ;
- `VAPID_PRIVATE_KEY`, `OPALE_ASK_API_KEY`, les identifiants Postgres.

Toute exécution de code dans ce process donne le contrôle total du parc Windows.
Le chemin le plus court n'est même pas le SSH : c'est la clé de signature. Un
attaquant signe un binaire agent malveillant, le dépose dans `dist/`, et
`HandleAgentUpdate` le distribue légitimement à chaque poste — où il s'exécute
en SYSTEM. La vérification ed25519 côté agent, par ailleurs bien faite
(`agent-go/update.go:61`), ne protège pas contre la compromission du signataire.

À noter que ce n'est pas un défaut d'implémentation mais un choix
d'architecture : mono-VM, mono-process, tout co-localisé. C'est cohérent avec la
cible « petite structure », mais le coût doit être explicite.

**Ce qu'il faut faire.**

- `USER node` dans les deux Dockerfile, `read_only: true` +
  `cap_drop: [ALL]` + `security_opt: [no-new-privileges:true]` dans les compose.
  Coût : quasi nul. Bénéfice : élimine l'escalade triviale post-RCE.
- Binder l'API sur la loopback : `ports: ["127.0.0.1:3010:3010"]`. Aujourd'hui
  `"3010:3010"` publie sur `0.0.0.0` — l'API en clair est joignable depuis
  Internet si l'hôte n'a pas de firewall, alors que l'installeur prévoit un
  reverse-proxy TLS devant.
- Sortir la signature du chemin chaud : signer les binaires hors-ligne (poste
  du mainteneur ou job CI dédié) et ne monter dans l'API que `signing.pub`. La
  clé de signature n'a aucune raison d'être accessible à un process qui répond
  à des requêtes HTTP publiques.
- Pour LAPS : exiger un motif (`parseReason`) comme le font déjà SSH et console,
  et déclencher automatiquement `rotation_requested_at` après consultation. Le
  code note d'ailleurs `TODO frontend` à cet endroit
  (`admin-credentials.js:34`), et le flag de rotation n'est consommé par aucun
  checkin (`admin-credentials.js:89`) — la fonctionnalité est incomplète.

## 5. Élevée — dépendances front tirées d'un CDN sans intégrité

`setup.sh` télécharge quatre bibliothèques au build :

```bash
curl -fsSL "https://cdn.jsdelivr.net/npm/@azure/msal-browser@3/lib/msal-browser.min.js" -o …
curl -fsSL "https://cdn.jsdelivr.net/npm/@tabler/icons-webfont@3.19.0/dist/tabler-icons.min.css" -o …
curl -fsSL "https://cdn.jsdelivr.net/npm/@xterm/xterm@5/lib/xterm.js" -o …
curl -fsSL "https://cdn.jsdelivr.net/npm/chart.js@4/dist/chart.umd.min.js" -o …
```

Trois problèmes cumulés :

1. **Ranges flottants** (`@3`, `@5`, `@4`) : le contenu change entre deux builds
   de la même version d'Opale. Les images ne sont pas reproductibles.
2. **Aucune vérification d'intégrité** : ni SRI, ni checksum, ni signature.
3. **Ces fichiers sont dans `.gitignore`** — donc rien dans le dépôt ne permet
   de détecter a posteriori qu'un build a récupéré autre chose que prévu.

Ce qui est téléchargé n'est pas anodin : `msal-browser` est la brique qui
manipule les jetons d'authentification de la console d'administration d'un RMM
disposant de SSH, LAPS et exécution de scripts. Une version compromise
(compromission jsDelivr, compromission du compte npm amont, empoisonnement DNS
sur la machine de build) exfiltre les jetons de toutes les instances qui
rebuildent.

La CI le vérifie d'ailleurs (`validate-docker-build` → « Verify vendored
frontend dependencies »)… mais seulement l'**existence** des fichiers, jamais
leur contenu.

**Ce qu'il faut faire.** Épingler les versions exactes et ajouter un fichier
`front/VENDORS.lock` avec les SHA-256, vérifiés par `setup.sh` (`sha256sum -c`)
et rejoués en CI. Une dizaine de lignes. Alternative plus propre à terme :
commiter les vendors ou passer par npm avec lockfile.

## 6. Moyenne-élevée — image non reproductible et runtime Node en fin de vie

**Lockfile ignoré.** Les deux Dockerfile font :

```dockerfile
COPY api/package.json ./
RUN npm install --omit=dev
```

`api/package-lock.json` existe dans le dépôt et est bien utilisé en CI
(`npm ci`), mais il **n'est pas copié dans l'image** et `npm install` est utilisé
au lieu de `npm ci`. Toutes les dépendances sont déclarées en ranges larges
(`"fastify": "^5"`, `"pg": "^8"`, `"jose": "^5"`…), donc l'arbre résolu dans
l'image publiée n'est pas celui testé en CI. Une version malveillante publiée
sur une dépendance transitive est intégrée au prochain build sans qu'aucun test
ne l'ait vue.

Correctif : `COPY api/package.json api/package-lock.json ./` + `RUN npm ci
--omit=dev`. Deux mots.

**Node 20 est EOL.** Le support de Node 20 s'est terminé en avril 2026 ; nous
sommes en juillet 2026. `node:20-alpine` dans les deux Dockerfile et
`node-version: '20'` dans les deux jobs CI signifient que l'API tourne sur un
runtime qui ne reçoit plus de correctifs de sécurité. Migration vers Node 22 LTS
(ou 24), en pinnant le digest de l'image de base tant qu'à faire.

**Tag flottant.** `ollama/ollama:latest` dans `docker-compose.yml` — même
problème de reproductibilité, sur un composant qui exécute des modèles sur les
contenus de mails entrants.

**Release non attestée.** `release.yml` publie sur GHCR sans cosign, sans SBOM,
sans provenance SLSA. Pour un produit installé par `curl | bash`, une
attestation `actions/attest-build-provenance` (une étape) apporte beaucoup.

**`ssh2` en dépendance racine.** Le `package.json` racine déclare
`"ssh2": "^1.17.0"`, mais aucun fichier hors `api/` ne l'importe (vérifié par
grep sur tout le dépôt). Dépendance morte, à supprimer — ou à documenter si
elle sert à un script non commité.

## 7. Moyenne — SSRF et exfiltration de la clé API via les settings

Trois URL de services LLM sont stockées en base et modifiables par un admin via
`PATCH /api/settings` : `ask.url`, `mail.classifier.url`,
`tickets.assistant.url`. Elles sont passées directement à `fetch()` sans
validation de schéma, d'hôte, ni blocage des plages privées.

Dans `settings.js:135-190`, `ask.enabled` et `ask.provider` sont bien validés
strictement (booléen, énumération fermée) — mais `ask.url` ne l'est pas du tout.

Deux conséquences :

- **SSRF** : le serveur émet un POST vers l'hôte choisi. La surface est bornée
  (chemin fixe `/v1/messages`, `/v1/chat/completions` ou `/api/chat`, méthode
  POST), donc l'exploitation vers un métadata service cloud est limitée, mais le
  scan du réseau interne par différenciation de latence/erreur fonctionne.
- **Exfiltration de secret**, plus direct : `provider.js:82` place
  `OPALE_ASK_API_KEY` dans l'en-tête `x-api-key` (ou `Authorization: Bearer`
  côté Mistral). Pointer `ask.url` vers un hôte contrôlé livre la clé API en
  clair au premier `POST /api/ask`. C'est précisément le risque que le commentaire
  de `ask.js:13` cherchait à éviter (« La clé API vient de l'env […] jamais des
  settings — anti-fuite via GET /api/settings ») : la clé ne fuit pas *en
  lecture*, elle fuit *en usage*.

C'est admin-only, donc ce n'est pas une élévation de privilège — mais c'est un
contournement du cloisonnement des secrets, et ça transforme un compte admin
compromis en exfiltration silencieuse.

**Ce qu'il faut faire.** Valider ces URL à l'écriture : schéma `https:` imposé
(sauf hôte Docker interne explicitement listé, `ollama`), rejet des IP privées
et de `localhost` hors allowlist, et idéalement une allowlist d'hôtes
(`api.anthropic.com`, `api.mistral.ai`, `ollama`) configurée par variable
d'environnement.

## 8. Moyenne — endpoint d'ingestion d'audit non authentifié

`POST /api/agent/setup-log` (`agent.js:501`) est **délibérément sans
authentification** — le commentaire l'explique : le script Intune tourne en
SYSTEM avant tout enrôlement. Le compromis est défendable, mais la mise en
œuvre laisse trois trous :

```js
const { hostname, script, level = 'info', log } = req.body || {}
if (!hostname || !log) return reply.code(400).send({ error: 'hostname et log requis' })
…
await logAudit(fastify.db, fastify.log, {
  action: 'setup_script', byUser: hostname, target: script || 'unknown',
  details: { level, log },
})
```

1. **Aucune borne de taille** sur `log`, `hostname` ou `script` — seul le
   `bodyLimit` Fastify par défaut (1 Mio) s'applique. À 60 req/min par IP, c'est
   ~86 Go/jour d'écritures dans `audit_logs` depuis une seule IP, et
   `plugins/cleanup.js` ne purge cette table qu'à 365 jours.
2. **Pollution du journal d'audit** : n'importe qui sur Internet peut insérer
   des entrées attribuées à un `by_user` arbitraire (le `hostname` fourni). Un
   attaquant qui a par ailleurs compromis un poste peut noyer les traces
   pertinentes sous du bruit crédible. Le journal d'audit d'un RMM est une pièce
   à conviction ; il ne devrait pas accepter d'écritures anonymes.
3. **Pas de séparation** entre entrées authentifiées et non authentifiées : rien
   dans la table ne distingue un `setup_script` d'un `ssh_open`.

Le rendu front est correctement échappé (`audit.js:247`, `esc(r.details.log)`),
donc pas de XSS ici.

**Ce qu'il faut faire.** Borner `log` (8 Kio) et `hostname` (255), marquer ces
lignes d'un flag `unauthenticated = true` et les afficher distinctement dans
l'UI, raccourcir leur rétention (30 j), et exiger à terme un bootstrap token —
le script Intune en embarque déjà un pour `exchange-token`, donc le coût est nul.

## 9. Moyenne — enrôlement d'agent : hostname revendiqué, token perpétuel

`POST /api/agent/exchange-token` (`agent.js:211`) est bien construit :
transaction + `SELECT … FOR UPDATE`, quota `bootstrap_max_redeems`, expiration.
Deux points restent faibles.

**Le device est retrouvé ou créé par hostname seul**, sans vérification :

```js
const { rows: dev } = await client.query('SELECT id FROM devices WHERE hostname = $1', [hostname])
```

Un porteur de bootstrap token (embarqué en clair dans le script Intune poussé à
N postes — donc lisible par tout utilisateur local sur l'un de ces postes) peut
donc réclamer un token personnel **lié à n'importe quel device existant**, en
annonçant son hostname. Il hérite alors du droit de remonter des résultats
d'exécution, un credential LAPS, et d'ouvrir une WebSocket agent pour ce device.
Le contrôle anti-cross-device du checkin (`agent.js:594`) ne rattrape pas ce cas,
puisque le token *est* légitimement lié à ce device_id.

**Le token émis n'expire jamais** — le commentaire le dit : « Token perso (sans
expiration — survit à la révocation du bootstrap) ». La rotation existe
(`/rotate-token`, grâce 24 h) mais elle est à l'initiative de l'agent ; un token
volé sur un poste reste valide indéfiniment tant qu'un admin ne le révoque pas
explicitement.

**Ce qu'il faut faire.** Refuser l'échange si le hostname correspond à un device
déjà rattaché à un token actif (ou exiger une correspondance de `serial`), et
poser une `expires_at` sur les tokens personnels en s'appuyant sur la rotation
existante pour les renouveler.

## 10. Moyenne — en-têtes de sécurité absents, jetons en `localStorage`

**CSP quasi inexistante.** `index.js:21` définit `const CSP = "frame-ancestors
'self'"`, appliquée uniquement au static et au fallback SPA. Pas de
`default-src`, pas de `script-src`, pas de `connect-src`, pas de `object-src`.
Aucun autre en-tête : ni HSTS, ni `X-Content-Type-Options`, ni `Referrer-Policy`,
ni `Permissions-Policy`. `@fastify/helmet` n'est pas dans les dépendances.

**Jetons dans `localStorage`.** `front/auth.js:18` configure MSAL avec
`cacheLocation: 'localStorage'` — au lieu du `sessionStorage` par défaut. Les
jetons d'accès survivent donc à la fermeture de l'onglet et sont lisibles par
tout JS s'exécutant sur l'origine.

Pris isolément, chacun est mineur. Combinés au style de rendu du front — 300+
affectations `innerHTML` avec interpolation de chaînes, aucun framework, aucun
échappement automatique — ils déterminent l'impact d'un unique `esc()` oublié :
vol de jeton admin d'un RMM avec SSH, LAPS et exécution de scripts.

Il faut souligner que la discipline d'échappement est **réellement bonne** : le
helper `esc()` (`app.js:14`) couvre les cinq caractères dangereux, `jsArg()`
traite correctement le cas des attributs `onclick`, et les points d'entrée
externes vérifiés (sujets et corps de mails entrants dans `tickets.js:2101`,
`2124`, `2180`, `2188` ; logs d'audit dans `audit.js:247`) sont tous échappés.
Aucune XSS n'a été identifiée. Mais la sûreté repose entièrement sur la
vigilance humaine, sans filet.

**Ce qu'il faut faire.** Ajouter `@fastify/helmet` avec une CSP réelle
(`default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none';
frame-ancestors 'self'`) — le front n'a ni CDN ni inline script, donc c'est
applicable sans refonte. Repasser MSAL en `sessionStorage`.

## 11. Moyenne — boucles et buffers non bornés

Plusieurs chemins traitent des entrées externes sans borne.

**Checkin** (`agent.js:523`). Les tableaux `disks`, `network`, `bandwidth`,
`ping` sont bouclés avec **une requête SQL par élément** :

```js
for (const disk of disks) { … await fastify.db.query(`INSERT INTO disks …`) }
if (network.length > 0) { await db.query('DELETE FROM network_interfaces …')
  for (const iface of network) { await db.query(`INSERT INTO network_interfaces …`) } }
for (const bw of bandwidth) { … }
```

Aucune borne sur la longueur. Un agent compromis (ou un simple bug côté agent)
envoie 1 Mio de JSON = plusieurs milliers d'INSERT séquentiels sur le pool de
10 connexions partagé par toute l'application. Correctif : plafonner chaque
tableau (`.slice(0, 64)`) et batcher via `unnest()` — le pattern est déjà
maîtrisé dans le dépôt (`users.js:163`).

**Exécution de scripts** (`scripts.js:185`) :

```js
await Promise.all(devices.map(async (device) => { … execOnDevice(…) }))
```

Aucune limite de concurrence. Sur un groupe natif de 200 postes, c'est 200
connexions SSH sortantes simultanées depuis le process API. De plus,
`execOnDevice` n'impose de timeout que sur la connexion (`readyTimeout: 10_000`),
pas sur l'exécution : un script qui ne se termine jamais laisse la promesse et le
flux SSE ouverts indéfiniment. Enfin `output` accumule tout en mémoire et n'est
tronqué (`slice(0, 100000)`) qu'*après* accumulation complète — un script
bavard peut faire tomber l'API en OOM.

**Index winget** (`winget-index.js`). Au boot (`plugins/winget.js:13`,
inconditionnel), l'API télécharge ~50 Mo de MSIX, l'extrait en mémoire, et
conserve une base SQLite complète chargée en WASM, rafraîchie toutes les 24 h.
Sur la VM unique de 10-200 postes visée, c'est plusieurs centaines de Mo de RSS
résident, en permanence, pour de l'autocomplétion de noms de paquets. Cela
justifie aussi deux dépendances (`sql.js`, `yauzl`) qui ne servent qu'à ça.

À noter aussi une incohérence entre commentaire et code au même endroit :

```js
// Pas de redirection vers un autre host : on attend uniquement le
// CDN MS, donc si jamais un middlebox tentait de rediriger ailleurs
// on préfère échouer.
redirect: 'follow',
```

`redirect: 'follow'` fait exactement l'inverse de ce que décrit le commentaire.
Il faut soit `redirect: 'error'`, soit corriger le commentaire.

**Ce qu'il faut faire.** Un helper `pMap(items, fn, { concurrency: 10 })`
(quinze lignes, zéro dépendance), un timeout d'exécution sur `conn.exec`, une
troncature à l'écriture dans les buffers, et rendre l'index winget opt-in
(setting `packages.winget_index_enabled`, défaut `false`) ou le déplacer dans un
sidecar.

## 12. Moyenne — la CI ne cherche pas de défauts

`ci.yml` est propre et bien commenté : tests API sur Postgres réel, matrice
cross-compilation Go, validation d'idempotence des migrations en double passe
(bon réflexe), parité i18n, smoke test Docker. Ce qui manque :

- **Aucun linter.** Le job s'appelle « Lint & test API » mais fait
  `node --check`, qui vérifie uniquement que le fichier parse. Sur 237 fichiers
  JS sans types, pas d'ESLint = aucune détection de variable non déclarée,
  `await` oublié, promesse non gérée, import mort.
- **Aucun audit de dépendances.** Ni `npm audit`, ni `govulncheck`, alors que
  Dependabot est configuré (il ouvre des PR, il ne bloque pas les merges).
- **Aucun SAST.** Pas de CodeQL, pourtant gratuit sur un dépôt public.
- **Aucun scan d'image.** L'image publiée sur GHCR n'est pas passée au Trivy/Grype.
- **Aucun scan de secrets.** Un dépôt qui manipule des clés SSH et de signature
  devrait avoir gitleaks en pre-commit et en CI. (Vérifié manuellement : rien
  n'est actuellement commité — `agent-go/keys/` ne contient que les `.pub`, et
  `.gitignore` couvre correctement `.env`, `signing.key`, `laps.key`,
  `intune-installers/`.)
- **Zéro test front.** ~1,2 Mo de JS applicatif, dont toute la logique de rendu
  et d'échappement, sans un seul test.

Ces cinq ajouts représentent une demi-journée et couvrent une bonne partie des
régressions futures.

## 13. Moyenne — desktop et mobile sont deux implémentations parallèles

`front/views/` et `front/views/mobile/` contiennent **19 fichiers chacun**, avec
les mêmes noms : `tickets.js`, `poste.js`, `postes.js`, `alertes.js`,
`conformite.js`, `stock.js`, `audit.js`, `scripts.js`, `packages.js`…

Le coût est visible dans le git log : plusieurs commits récents (`#52`, `#54`,
`#56`, `#60`) portent explicitement « parité mobile » — c'est-à-dire le travail
de rattrapage d'une divergence structurelle. `front/views/tickets.js` fait 2776
lignes, `front/views/mobile/ticket.js` 840 : chaque évolution fonctionnelle doit
être écrite, testée et débuguée deux fois, et chaque correctif de sécurité aussi
(un `esc()` oublié dans une seule des deux branches suffit).

C'est le principal frein à l'évolutivité du front, devant l'absence de framework.

**Ce qu'il faut faire.** Extraire les couches partageables sans réécrire l'UI :
appels API, normalisation des données, formatage (dates, tailles, énumérations),
composants de rendu atomiques (badges, chips de tags, liens device/user). Viser
le partage de la logique, pas du layout. Cela peut se faire incrémentalement,
vue par vue, sans big bang.

Dans le même registre, `api/modules/inventory/routes/agent.js` fait 1174 lignes
et `checkin` à lui seul en concentre ~400 : upsert device, disques, interfaces,
bande passante, ping, métriques, santé, tamper, résultats de déploiement,
résultats de détection, évaluation de conformité, décision de mise à jour,
fenêtre de maintenance. C'est un point de passage obligé pour tout le parc,
sans transaction englobante — un échec au milieu laisse un état partiel. À
découper en handlers par section, orchestrés dans une transaction.

## 14. Faible — divers

**Verrouillage admin.** `PATCH /api/settings/admins/:entraId`
(`settings.js:279`) n'empêche ni la révocation du dernier admin, ni
l'auto-révocation. Combiné à l'absence de bootstrap premier-admin (§1), un seul
clic peut rendre l'instance inadministrable, sans autre recours que psql.
Correctif : refuser si le compte cible est le dernier `is_admin`, et refuser
l'auto-révocation.

**WebAuthn décoratif.** `front/biometric.js` est honnête dans son en-tête
(« vérification côté appareil uniquement »), mais le README annonce « WebAuthn
unlock » parmi les fonctionnalités de sécurité de la PWA. En réalité : challenge
généré côté client, aucune vérification serveur de la signature, aucun
enregistrement de la clé publique côté API. Le contournement est
`localStorage.removeItem('rmm-bio-cred')` — ou simplement un appel direct à
l'API, qui ignore complètement l'état de verrouillage. C'est un verrou d'UI, pas
un contrôle de sécurité ; il faudrait le nommer ainsi dans le README pour ne pas
créer une fausse assurance.

**Branding en dur dans les prompts.** `ask/lib/prompt.js:34` et
`tickets/lib/assistant.js:11` contiennent en dur « organisation Tour du Valat,
institut de recherche sur les zones humides ». Sur un produit AGPL destiné à
être auto-hébergé par des tiers, tout déployeur envoie ce contexte à son
fournisseur LLM. Le mécanisme existe déjà : `org.name` est un setting, et le
pre-prompt assistant est configurable (migration `067`). Il suffit de
l'interpoler.

**Chaîne PostgreSQL sans TLS.** `plugins/db.js` n'active pas `ssl`. Acceptable
tant que la base est sur le même hôte Docker, mais `POSTGRES_HOST` est
documenté comme pouvant être « une adresse IP » — dans ce cas les identifiants
et toutes les données circulent en clair. À rendre configurable via
`PGSSLMODE`.

**Validation d'entrée quasi absente.** 7 routes sur 150 déclarent un `schema:`
Fastify — uniquement dans `stock.js` et `alert-snoozes.js`. C'est pourtant le
mécanisme natif de durcissement du framework : validation JSON Schema, coercition
de types, et surtout sérialisation de sortie (qui évite de renvoyer par
inadvertance des colonnes sensibles via les nombreux `SELECT *` du code —
`agent.js:174`, `scripts.js:148`, `deployments.js:112`…). Ajouter au moins les
`response` schemas sur les routes qui font `SELECT *`.

**`.env.example` incomplet.** Manquent `OPALE_ASK_API_KEY`, `ATTACHMENTS_DIR`,
`LAPS_PRIVATE_KEY`, `AGENT_GO_DIR`, `WINGET_SOURCE_URL`, `OLLAMA_PULL_MODEL` —
tous lus par le code. Un déployeur qui suit le fichier obtient une configuration
partielle sans message d'erreur.

**Pas d'arrêt propre.** Aucun handler `SIGTERM`/`SIGINT` : `docker compose
restart` coupe les requêtes en vol, les sessions SSH et les WebSockets agent
sans fermeture propre.

**Dette explicitement documentée.** Plusieurs commentaires signalent du code
non fini ou en attente de nettoyage : le flag de rotation LAPS non consommé
(`admin-credentials.js:89`), les tokens CLI legacy hex64 sans préfixe à retirer
(`plugins/auth.js:113`), les stores en mémoire (grants, sessions console,
registre WS agent) qui interdisent tout scale-out multi-instance — bien
identifiés, avec le chemin Redis indiqué, mais à traiter avant d'envisager la
haute disponibilité.

## 15. Ce qui est bien fait

Il serait trompeur de terminer sans le dire, d'autant que ces points doivent
être préservés lors des correctifs ci-dessus.

- **Chaîne de mise à jour de l'agent** (`agent-go/update.go`) : SHA-256 puis
  ed25519 avant écriture, remplacement atomique par `rename`, état persisté,
  rollback après 2 checkins échoués, `semverGT` qui bloque les downgrades. TLS
  1.2 minimum, pinning SPKI optionnel *en plus* de la validation CA (jamais à la
  place), aucun `InsecureSkipVerify` dans le dépôt. C'est fait correctement.
- **Module `ask`** (LLM → SQL) : le registre whitelisté est la seule source des
  identifiants SQL, seules les valeurs passent en `$n`, la validation
  (`queryspec.js`) est explicitement documentée comme la frontière de sécurité,
  et le LLM ne voit jamais le schéma. C'est la bonne architecture pour ce
  problème — beaucoup de projets se contentent de faire générer du SQL.
- **Grants one-shot** (`one-shot-grant.js`) : nonce de 32 octets, TTL 30 s,
  consommé même en cas d'échec (pas de retry), auto-nettoyage `unref()`. Le
  raisonnement documenté — ne pas passer le JWT en query string à cause des
  access logs Caddy, du Referer et des caches — est juste et rarement anticipé.
- **Module console-via-agent** : re-vérification agent en ligne *et* capability
  entre le grant et l'upgrade WS, gestion explicite du takeover avec audit
  dédié, frames plafonnées à 64 Kio, heartbeat avec codes de fermeture typés.
- **Traçabilité** : motif obligatoire et validé pour SSH et console, sessions
  journalisées, durées de rétention RGPD différenciées et justifiées
  (`cleanup.js` : 30 j pour les frames terminal contre 183 j pour les
  métadonnées, avec le raisonnement écrit). La note RGPD sur `sync-all`
  (`users.js:175`) montre que le sujet est traité sérieusement.
- **SQL** : paramétré partout ; les trois interpolations restantes
  (`bandwidth.js:279` via whitelist `TOP_SORTS`, `devices.js:39` via `parseInt`,
  `cleanup.js` via constantes) sont sûres et deux d'entre elles sont
  explicitement justifiées en commentaire.
- **Pièces jointes** (`attachments.js`) : nom d'origine jamais dans le chemin
  disque, `resolveAttachmentPath` revérifie le confinement sous la base,
  `Content-Disposition: attachment` systématique avec RFC 5987. Propre.
- **Couverture de tests API** : 70 fichiers de test, y compris sur les libs
  pures (compile, queryspec, resolve, matching de threads mail, buffers de
  session, grants). C'est substantiel.
- **Qualité des commentaires** : ils expliquent les décisions, les incidents de
  production qui les ont motivées (le cas RESTCHIREAU dans `checkin`, le doublon
  de migration `048`) et les compromis assumés. C'est ce qui a rendu cette revue
  rapide, et c'est un atout durable pour le projet.
