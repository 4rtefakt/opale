# Opale — Linux agent and image (`opale-linux-agent`): design

Status: v1 (2026-10-01). Agent-side counterpart of `docs/linux-fleet-design.md` (server design, §1 identity, §3 OOBE contract, §4 agent API, §9 decisions) and `api/modules/linux/openapi.yaml` (the wire contract; operationIds cited inline). Three proposals (Go daemon, bash + timer, Python + timer) were judged on security, simplicity, OOBE, maintainability and testability; the Go daemon won on both panels and this document is that proposal with the judges' grafts and the adversarial review folded in.

**Review log.** Adversarial review, 3 lenses (security, contract, ops): 50 findings, 43 distinct after merging 7 cross-lens duplicates. **43 folded, 0 rejected**; every contract finding was re-verified against the server code it cites (`routes/git.js:34`, `lib/enrollment.js:199`, `lib/checkin.js:83`, `api/lib/retention.js:26`, `lib/spec.js:70-74`, `openapi.yaml` 1135/1160/1191/1274) and holds. Two findings were corrected while folding: the "proper" privilege-split fix is only true if the root side re-verifies the commit and exports the tree itself (§10), and the GDM compiled-db path is a detail that does not change the fix (§3). Net architectural changes vs the draft: daemon runs as an unprivileged user with every mutation in a static root template unit; `extra_vars` is an allowlist; LUKS bootstrap keyfile in the initrd, TPM2 + Secure Boot are install-time requirements, PIN is the recommended laptop default (§17 Q2); `rejected`/`serial_mismatch` are terminal like `revoked`; watchdog pinged from the sleep loop; any post-check-in abort produces a `failed` report.

Goal (user): "Opale serves configs for our custom ISO to pull its goal state from and deploy it" — clean OOBE, users moved from Windows to Linux progressively, devices only make outbound HTTPS, no secrets in the image, no arbitrary-command feature, least privilege.

## 0. Shape in one paragraph, and the decisions the proposals disagreed on

A new top-level Go component `agent-linux/` (module `github.com/4rtefakt/opale/agent-linux`, toolchain aligned on `agent-go/go.mod`), built as one static binary `opale-linux-agent` and shipped as a `.deb`. It runs as a sandboxed, **unprivileged** long-running daemon (`opale-linux-agent.service`, `User=opale-agent`, `Type=notify`) that owns the device key, signs requests, enrols, checks in, fetches and **verifies** the fleet repo, and reports; everything that mutates the system (hostname, signer rotation, `ansible-playbook`, `useradd`/`chpasswd`, `cryptsetup`, GDM banner) runs in a short-lived instance of a static root template unit `opale-linux-apply@.service`, fed a closed-schema job file, which **re-verifies the commit signature itself and exports the tree into its own tmpfs** before running anything. A one-time `opale-linux-oobe.service` owns tty1 before the greeter, shows the 8-char enrolment code, and runs the first apply inline so the assigned user exists at the first login screen. The image is a Debian 13 (trixie) netinst remastered with a preseed (per-device LUKS2 master key, nothing to strip), bootstrap keyfile in the initrd for the first boot, TPM2 auto-unlock (PCR 7, PIN recommended for laptops) via dracut, recovery key escrowed to Opale. Agent updates ride the signed fleet commit (`.deb` pinned by sha256 in a profile), never an in-band binary channel.

| Question | Decided | Why (short) |
|---|---|---|
| Language / runtime | Go, separate module, copy (not import) portable pieces of `agent-go` | Same mental model as the Windows agent (signing helpers, atomic writes, escrow-first stash, interop vectors); SPKI pinning on the verified chain; typed handling of secrets; no bash/argv leaks, no Python matrix. |
| Process model | Daemon (`Type=notify`) with internal scheduler | `checkin_interval_s` is server-driven, enrol polling is 30 s/300 s, backoff/nudges are natural in a loop. The design §1 guarantee ("revoked ⇒ exit 0, no crash loop") is kept with `Restart=on-failure` + `ConditionPathExists=!…`. Timer+oneshot stays the documented fallback (§15). |
| Git stage | Agent-driven `fetch` → `verify-commit FETCH_HEAD` → `reset --hard`; root side re-verifies and `git archive`s the tree | The tree is verified before anything reads it, twice (daemon pre-check, root side authoritative); git-stage vs play failures are separated by exit code; `revision` is `rev-parse HEAD`. Same packages and trust semantics as the `ansible-pull` line in design §4 (§14 aligns the text). |
| Skip rule | `apply_hash` (revision + profile + ring + extra_vars) vs last **success** + 24 h full apply | `--only-if-changed` silently hides a failed apply until the next commit and never corrects drift. |
| Privileges | Unprivileged daemon + root template unit started through a polkit-scoped `systemctl start` | A compromise of the HTTP/JSON/git path yields the `opale-agent` user, who can only start jobs whose content the root side validates and re-verifies — not root. The split is real, not accident containment (§10 says what is still accepted). |
| Self-update | `.deb` installed by a profile task, sha256 pinned in the signed commit, downgrade-guarded | Reuses the only trust chain that exists (signed commit + pinned CA); no central signing key, no new server route, no apt repo infrastructure. |
| Image | Debian 13, debian-installer + preseed, no golden image | Fresh LUKS key, machine-id, seeds and host keys per device; nothing to strip but `/var/log/installer`. |
| OOBE | tty1 full-screen page (code + status) before the greeter, bounded hold 30 min, then GDM banner | Deterministic, works with zero users, releases the device when Opale is unreachable; the code is also derivable from the key (`fp[:8]`). |
| End-user account | Created by the profile playbook (`ansible.builtin.user`), gnome-initial-setup disabled | Autopilot-like "device is ready, log in"; needs `opale_assigned_user` in `extra_vars` (§14) and the first-apply `opale_initial_password` channel (§6.8, §17 Q4). |

Conventions: stdlib `testing` only (CONTRIBUTING.md:45), tests on macOS for pure code, build tags for Linux-only files; commit scope `agent-linux`; `go.mod` pinned to the same Go line as `agent-go` (1.26). What is **not** inherited: Bearer-token identity and rotation, the checkin command/deployment/detect queue, PowerShell/winget exec, the WebSocket console, runtime-config, the ed25519 self-update/rollback machinery, the embedded `laps.pub`, the hardened Windows-style unit, the `instance-local` build-time branding (the device needs a config file, not link-time symbols).

## 2. Identity, signing, TLS

**Key.** On first run (`oobe` or `run` with no key): `crypto/ed25519` keypair, PKCS#8 PEM at `/var/lib/opale-agent/key` (0600 `opale-agent`, directory 0700 via `StateDirectory=opale-agent` + `StateDirectoryMode=0700`), written **create-then-rename with `O_EXCL`** on the temporary name so a second creator (OOBE and daemon racing, §3) reads the winner instead of overwriting; plus a copy of `/etc/machine-id` at `/var/lib/opale-agent/machine-id`. Every start compares the copy with `/etc/machine-id`; a mismatch (cloned disk) deletes key, state and markers and re-enrols with a new fingerprint (design §1). `key_backing = software` in v1; `tpm` is PR 6: the PEM is sealed with `systemd-creds encrypt --with-key=tpm2` into `key.cred`, the units carry `LoadCredentialEncrypted=`, the agent reads `$CREDENTIALS_DIRECTORY/opale-key`, the plaintext PEM is removed. Sealing, not a TPM-resident key — the server accepts both values without further semantics (`EnrollRequest.key_backing`).

**Fingerprint and code.** `fingerprint = hex(sha256(raw 32-byte public key))` (lowercase 64 hex); `public_key` in `linuxAgentEnroll` = base64 of the raw 32 bytes (43 chars + `=`); the server derives the fingerprint and requires it to equal `x-opale-key` (`device-auth.js:49-57`). The enrolment code is `fingerprint[:8]`, so `opale-linux-agent status` can always print it for support.

**Signing** (`internal/sign`, spec §"Signed requests" and `device-auth.js:13-15`): headers `x-opale-key`, `x-opale-timestamp` (unix seconds + `clock_offset_s`), `x-opale-nonce` (16 random bytes → 32 hex), `x-opale-signature` (std base64 of the 64-byte Ed25519 signature over the raw canonical bytes, no pre-hash); `canonical = "opale-linux-v1\n" + METHOD + "\n" + path_with_query + "\n" + timestamp + "\n" + nonce + "\n" + hex(sha256(body))`. `path_with_query` is the full request target as nginx will hand it to Fastify (`/api/linux/agent/checkin`); the body is marshalled once into a single `[]byte` that is both hashed and sent; `Content-Type: application/json` is forced (the plugin only parses that type); an empty body hashes as sha256 of zero bytes.

**JSON encoding rules** (contract): `EnrollRequest.serial`, `CheckinRequest.serial` and `ReportRequest.revision` are `required` **and** nullable (`openapi.yaml` 1135-1137, 1191-1193, 1274-1276); the Go structs use `*string` **without `omitempty`** so a placeholder serial or a failed git stage is sent as an explicit `null` — an omitted key is a `400` from Ajv, and on `/enroll` that would strand the OOBE. The interop vectors (below) include a placeholder-serial enrol body and a `revision: null` failed report.

**Validation of server strings.** Every server-supplied string that later reaches argv, a file or a playbook variable is validated against the spec regexes before use: hostname `^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$`, profile `^[a-z0-9][a-z0-9-]{0,63}$`, ring ∈ {pilot, stable}, revision 40-hex, `device_id` uuid, `local_admin_username` **client-side** `^[a-z_][a-z0-9_-]{0,31}$` (stricter than the server's `^[A-Za-z0-9_.-]{1,32}$`: refuses `-foo`, which `useradd` reads as an option, `.`/`..`, and names outside Debian's `NAME_REGEX`; refusal = `USERNAME_INVALID` event, step disabled), key_id 64-hex, `git.url` byte-equality with `OPALE_URL + "/api/linux/agent/git/fleet.git"`, `extra_vars` restricted to the §6.8 allowlist. A failed validation aborts the cycle with an `assignment-invalid` event **and a `failed` report** (§7: nothing is applied, and the admin sees why).

**Interop.** `api/scripts/linux-signing-vectors.mjs` uses `device-auth.js` `signRequest`/`canonicalString` and the `api/tests/helpers/linux-agent.js` key handling to emit `agent-linux/internal/sign/testdata/vectors.json` (private key PEM, method, target, body, timestamp, nonce, expected headers and canonical string). The Go test replays them byte for byte (same approach as `agent-go/interop_test.go`); the vectors are committed and CI regenerates them and fails on diff, so a change to the canonical string on either side is caught.

**TLS.** One `http.Client`: `MinVersion` TLS 1.2, `RootCAs` loaded from `OPALE_CA_FILE` only (no system store — no TOFU on an imaging network, design §1), `VerifyPeerCertificate` applying `OPALE_SPKI_PINS` to the *verified* chain when set, never `InsecureSkipVerify` (a static test greps for it), 30 s timeout per request, no TLS session cache. git gets the same CA through `/etc/opale-agent/gitconfig` (`http.<OPALE_URL>/.sslCAInfo`, `http.followRedirects=false`), loaded through `GIT_CONFIG_SYSTEM=/etc/opale-agent/gitconfig GIT_CONFIG_GLOBAL=/dev/null` so no other git configuration on the device can interfere. **git is not SPKI-pinned**: libcurl's `pinnedPubkey` compares the *leaf* SPKI only, so an intermediate/CA pin (valid for the agent) would break every fetch and a leaf pin would break at each certificate renewal; the CA file is git's anchor. `OPALE_SPKI_PINS` therefore hardens the signed API calls only, and the doc for the setting says so.

## 3. Enrolment and OOBE

Units involved, in order (`After=` chain stated once here, repeated in §10): `opale-linux-luks-prepare.service` (root, §9) → `opale-linux-oobe.service` → `opale-linux-agent.service` (`After=opale-linux-oobe.service`, `Wants=opale-linux-oobe.service`). Because the OOBE unit is `Type=oneshot`, systemd starts the daemon only after the OOBE `ExecStart` has exited: **exactly one process owns the key during the hold and the inline first apply** — no double enrol, no double check-in against the 12/h budget, no two writers on `state.json` or the fleet checkout.

`opale-linux-oobe.service` (`Type=oneshot`, `User=opale-agent`, same sandbox as the daemon, `ConditionPathExists=!/var/lib/opale-agent/approved`, `After=network-online.target time-sync.target opale-linux-luks-prepare.service`, `Wants=network-online.target` — never `systemd-time-wait-sync.service`, which blocks forever offline; `Before=display-manager.service getty@tty1.service opale-linux-agent.service`, `TTYPath=/dev/tty1`, `StandardInput=tty-force`, `StandardOutput=tty`, `ExecStartPre=+-/usr/bin/plymouth quit`, `ExecStartPre=+/usr/bin/opale-linux-agent cache-facts` (reads the 0400 DMI serial as root into `/var/lib/opale-agent/facts.json`, §10), `TimeoutStartSec=infinity` — the hold timer and the apply unit's `RuntimeMaxSec` bound it; a 40-min cap would kill an approval that arrived at minute 29 mid-apply) runs `opale-linux-agent oobe`:

1. Identity created if missing (§2). Facts: `serial` from the cached DMI facts with the server's placeholder list applied client-side (`device-claim.js:27-38`: empty, `unknown`, `System Serial Number`, `To Be Filled By O.E.M.`, `Default string`, `0`, … → `null`, sent as JSON `null`); `hostname` from `/etc/hostname` (placeholder `opale-pending` set by the image); `os_version` = `PRETTY_NAME`; `kernel` = uname release; `agent_version`; `key_backing`; `public_key`.
2. `POST /enroll` (`linuxAgentEnroll`) every `retry_after_s` (30 s for the first hour, then 300 s; ±20 % jitter), under the 30/min per-IP limit even behind an imaging-room NAT (a `429` sleeps `max(Retry-After, retry_after_ms)`).
3. Screen: a full-width text page — Opale, serial, the code in 5-line block letters, and a status line: « En attente d'approbation (prochaine tentative dans 30 s) », « Conflit (<kind>) — en attente de décision de l'administrateur » when `conflict` is non-null (`EnrollPending.conflict` carries **only `kind`** ∈ {existing_device, reimage, clone} on the wire — `openapi.yaml:1160-1164`; `schemaFor()` installs the response schema and the serializer strips the `hostname`/`device_id` that `enrollment.js` builds; the target hostname is visible in the admin queue only), « Approuvé : <hostname> — préparation du poste… », « Refusé — contactez le support (code XXXXXXXX) », « Clé révoquée », « Numéro de série différent », « Serveur injoignable depuis N min ». The code is also written to `/var/lib/opale-agent/enroll-code`.
4. `200 approved` → `approved` marker (contains `device_id`), then the **first cycle runs inline** (§6: check-in, hostname, local-admin creation, git stage, play, report) before the unit exits, so the greeter appears with the assigned user already created by the profile. The screen tails the progress file the apply unit writes (task names only, §10) and, after a `success` report, shows the one-time values of §17 Q4 (initial password, and the TPM PIN when Q2 picks PIN mode) until a key is pressed or 10 min elapse. While no `luks_recovery` escrow has succeeded (§9) the page says « Clé de récupération non séquestrée — ne pas remettre le poste » instead of « Poste prêt ».
5. Terminal states: `403 REJECTED` / `REVOKED` / `SERIAL_MISMATCH` → marker written, message stays up for 10 min, then exit 0. All three are final for this key (§4): the daemon's `ConditionPathExists` makes every later start a no-op, and the support path is `opale-linux-agent reset`.
6. **Bounded hold.** After 30 min still `pending` (or server unreachable) the unit requests the privileged job `gdm_banner` (§10) which writes `banner-message-enable=true` / `banner-message-text='Opale — code d'enrôlement : XXXXXXXX'` into `/etc/gdm3/greeter.dconf-defaults` and runs `systemctl reload gdm3.service` (Debian's `generate-config` recompiles the greeter db on reload; `dconf update` only compiles `/etc/dconf/db/*.d` and does nothing for the greeter; a reload restarts only the greeter, never a logged-in session), then exits 0; GDM starts (user-less), `opale-linux-agent.service` continues polling, the banner is replaced by « Poste prêt » on approval and removed after the first successful apply (same job, empty text).

The image sets `InitialSetupEnable=false` in `/etc/gdm3/daemon.conf` and hides `gnome-initial-setup-first-login.desktop` + `gnome-tour`: user creation is the profile's job, driven by `opale_assigned_user` (§14). Zero users at first boot is guaranteed by the preseed (§12): `passwd/root-login true`, `passwd/make-user false`, `passwd/root-password-crypted` = a real crypt(3) hash of a per-install random value generated in `early_command` and never recorded — `user-setup` forces `make-user true` when root login is disabled and treats `!` as "not preseeded", so "locked root + no user" is not expressible directly; a random unknown root password is equivalent in practice.

## 4. State machine and server responses

State file `/var/lib/opale-agent/state.json` (atomic, 0600): `status ∈ {new, pending, approved, rejected, revoked, serial_mismatch}`, `device_id`, `conflict`, `clock_offset_s`, `backoff_n`, `not_before`, `last_checkin_at`, `checkins` (sliding window of the last hour's check-in timestamps, §5), `last_status`, `last_revision`, `last_success_hash`, `last_full_apply_at`, `last_reported_hash`, `last_reported_cause`, `local_admin {rotated_at, key_id}`, `luks {slot, key_id, pcr7, escrowed}`, `signers_sha256`, `first_apply_done`. Markers as files for `ConditionPathExists=`: `approved`, `revoked`, `rejected`, `serial_mismatch`.

| Response (`{error, code}`) | Agent reaction |
|---|---|
| `202 pending` (`code`, `retry_after_s`, `conflict{kind}`) | `pending`; display; poll at `retry_after_s`. |
| `200 approved` (`device_id`, `hostname`) | `approved`; immediate check-in. |
| `401 CLOCK_SKEW` (+ `server_time`) | `clock_offset_s = server_time − now`, persisted, retry once immediately. Offset kept until `/run/systemd/timesync/synchronized` exists (created by timesyncd on first sync — no `timedatectl` exec), then zeroed. |
| `401 NONCE_REPLAY` | new nonce, retry once. |
| `401 SIGNATURE_INVALID` | bug or a proxy rewriting the request target: `error` event, abort cycle, normal backoff; never regenerate the key. |
| `401 UNKNOWN_KEY` / `NOT_APPROVED` on checkin/reports/escrow | remove `approved`, back to `pending` with the **same key**; next cycle calls `/enroll` (device deleted server-side re-enters the queue once as pending, design §1). At most one enrol per cycle, no limit. |
| `401 REVOKED` on a **signed route** | `revoked` marker, « poste révoqué » banner, `exit 0`. `ConditionPathExists=!…/revoked` keeps every later start a no-op (`systemctl status` shows the condition). Only `opale-linux-agent reset` (root, local) or a re-image produces a new key; the old fingerprint stays revoked. |
| `401` on the **git route** (any code) | git surfaces only "error: 401"; `routes/git.js:33-34` also answers `REVOKED` for a *missing* key row (device deleted between check-in and fetch — token TTL 10 min), which the signed routes report as `UNKNOWN_KEY`. So a git 401 is never authoritative: treat as the transient git-stage rule (sleep 30 s, re-check-in, retry once); the re-check-in's own code (`REVOKED` vs `UNKNOWN_KEY`) decides. |
| `403 REJECTED` | `rejected` marker, message with the code, `exit 0` — **terminal**, like `revoked`: `approveEnrollment` refuses any non-`pending` key (`enrollment.js:199`, `409 NOT_PENDING`), no route moves `rejected` back, retention purges `pending` rows only (`retention.js:26`). Support path: admin revokes/deletes as needed, `opale-linux-agent reset` on site → new key → lands in the queue as `reimage` → approve with `supersede`. |
| `403 SERIAL_MISMATCH` (enrol or check-in) | `serial_mismatch` marker, `error` event, `exit 0` — **terminal** for the same reason: `serial_claimed` is written only by `/enroll` (`enrollment.js:117-118`, never for an approved key) and by `/checkin`'s `COALESCE` when NULL (`checkin.js:83`); no admin route edits it or `devices.serial`. Same `reset` support path. |
| `429 ENROLL_FLOOD`, `429 DEVICE_RATE_LIMIT`, plugin `429`, `5xx`, transport error | `not_before = now + max(Retry-After, retry_after_ms, full_jitter(30 s · 2^n, cap 1 h))`, `n++`; `n` reset on the next 2xx. |
| `git: null` (+ `retry_after_s`) | no git stage, no play, no report; next check-in after `max(retry_after_s, 600 s)`. |
| git fetch failure: transport, `401`, `503 MIRROR_NOT_READY` / `BUSY` | transient git-stage failure: sleep 30 s, re-check-in (fresh token), retry once, then report `failed` with `revision: null` (design §4, spec `linuxAgentCheckin` description). RAM-only token store on the API: an API restart mid-fetch is this case, not a fatal error. `verify-commit` failure is **not** retried (§6.5). |
| `409 ESCROW_STALE` | discard the stash; next cycle regenerates with `rotated_at = max(now + offset, stored rotated_at + 1 s)` (the agent knows its last accepted value from the previous `201`). If the clock stepped **backwards** (NTP) the step is disabled until `/run/systemd/timesync/synchronized` exists and `now > stored rotated_at`, then retried once — never a regenerate-every-cycle loop. |
| `409 ESCROW_KEY_MISMATCH` | discard the stash, regenerate (new secret, PEM re-read from the next assignment); never re-send. |
| `409 ESCROW_BACKUP_UNCONFIRMED` / `503 ESCROW_UNAVAILABLE` / `escrow.status ≠ ok` | quiet skip, one `info` event per state change, retry next cycle. |
| `400 USERNAME_MISMATCH` / `CIPHERTEXT_SIZE` / `ROTATED_AT_IN_FUTURE` / schema 400 | agent bug: `error` event, the step is disabled until the assignment changes, **one `failed` report** (§7); never retried in a loop. |

## 5. Cadence, jitter, backoff, nudges, watchdog

The daemon loop: `sleep(checkin_interval_s + uniform(0, 90 s))` **before** the check-in (design §4: jitter before, apply in the same cycle); `checkin_interval_s` is taken from the last assignment (900 default) and clamped to `[600 s, 24 h]`. `/etc/NetworkManager/dispatcher.d/90-opale` runs `systemctl kill -s USR1 opale-linux-agent.service` on `up` / `connectivity-change full`; the daemon starts a cycle only if `last_checkin_at` is older than **15 min** (except while `pending`, where it just re-polls `/enroll`). **Budget**: every check-in (scheduled, nudge, git-retry re-check-in) is counted against a local sliding window of 12/h (`state.checkins`); a nudge or retry that would exceed it is skipped with an `info` event — the `429 DEVICE_RATE_LIMIT` of `routes/agent.js:67` is then a bug signal, not a steady state. Reports ≤ 1 per cycle (+ the §7 abort report); escrow ≤ 2 per cycle (6/min); git ≤ 2 requests per fetch (30/min).

**Lifecycle with systemd.** `sd_notify(READY=1)` right after the state file is loaded (before the first tick — a first tick that includes a cycle would exceed the default `TimeoutStartSec=90s`). `WATCHDOG=1` is sent from a **60 s ticker that runs during the sleep and while waiting on an apply unit**, independent of cycles; `WatchdogSec=5min` is therefore a pure liveness bound (a hung HTTP or git call is already bounded by the 30 s / 300 s timeouts; a wedged apply by `RuntimeMaxSec=1800` on the apply unit). `Restart=on-failure`, `RestartSec=30`, `RestartForceExitStatus=75` (§11), so a clean `exit 0` (revoked/rejected/serial_mismatch) is final, a crash is restarted, and a requested re-exec is restarted. Laptops: a cycle that was due during suspend runs at resume (monotonic clock), then normal cadence. Backoff after a bad cycle never lengthens the scheduled cadence beyond 1 h.

## 6. Apply cycle (check-in → hostname → escrow → git → signers → play → report)

Run by the daemon (`opale-agent` user); steps marked ⚙ are jobs executed by the root template unit (§10). A job is `{job_version: 1, kind, …typed fields}` written to `/run/opale-linux-agent/jobs/<n>.json` (0640, daemon-owned, the root side reads it), started with `systemctl start opale-linux-apply@<n>.service` (blocks until the oneshot completes), result read from `/run/opale-linux-agent/jobs/<n>.result.json` (written by root, 0640 `root:opale-agent`).

1. **Facts and check-in** (`linuxAgentCheckin`): `serial` (normalised as in §3, explicit `null` when placeholder), `agent_version`, `os_version`, `kernel`, `hostname` (current), `uptime_s`, `disk_root_pct` (Statfs on `/`), `luks_root` (`/sys/class/block/<root dm>/dm/uuid` starts with `CRYPT-LUKS`, one DM level, as `agent-go/health_linux.go:77-89`), `escrow_key_id` (= `state.local_admin.key_id`), `local_admin_rotated_at`. The serial re-check is the server's (`403 SERIAL_MISMATCH` → §4).
2. **Assignment validation** (§2 regexes, `git.url` equality, `extra_vars` allowlist). Cache `escrow.public_key_pem` and `key_id` in memory for this cycle only, after checking `key_id == hex(sha256(SPKI DER of the PEM))`.
3. ⚙ **Hostname** when `assignment.hostname ≠ current`: job `{kind:"hostname", hostname}` → `hostnamectl set-hostname`, rewrite the `127.0.1.1` line of `/etc/hosts` (Debian's `sudo: unable to resolve host` trap). Server-assigned, never the agent's claim (design §3 hostname rule).
4. ⚙ **Local admin** and **LUKS escrow** when triggered (§8, §9). Fast, independent of the play; failures log and continue.
5. **Git stage** (daemon, in its own `StateDirectory`): first run `git init /var/lib/opale-agent/fleet` + `remote add origin <git.url>`; then
   ```
   GIT_TERMINAL_PROMPT=0 GIT_CONFIG_SYSTEM=/etc/opale-agent/gitconfig GIT_CONFIG_GLOBAL=/dev/null
   GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=http.<git.url>.extraHeader GIT_CONFIG_VALUE_0="Authorization: Bearer <token>"
   git -C fleet fetch --depth 1 origin +refs/heads/<ring>:refs/remotes/origin/<ring>      # linuxAgentGitInfoRefs + linuxAgentGitUploadPack
   git -C fleet verify-commit refs/remotes/origin/<ring>                                     # pre-check against the pinned signers (root re-verifies, §10)
   git -C fleet reset --hard refs/remotes/origin/<ring> && git -C fleet clean -fdx
   revision=$(git -C fleet rev-parse HEAD)
   ```
   The token lives in the git child's env for the fetch only (never argv, never disk, never the play). `/etc/opale-agent/gitconfig`: `gpg.format=ssh`, `gpg.ssh.allowedSignersFile=/var/lib/opale-agent/trust/allowed_signers`, `gpg.ssh.revocationFile=/var/lib/opale-agent/trust/revoked_signers`, `http.<url>.sslCAInfo`, `http.followRedirects=false`, `protocol.allow=never` + `protocol.https.allow=always`, `safe.directory=/var/lib/opale-agent/fleet` (the root side reads a repo owned by another user). The ring **branch** is fetched (shallow works, design §2); `assignment.revision` is logged when ≠ HEAD (pilot auto-advance race) but HEAD is what is applied and reported. **Failure attribution**: `fetch` failures (transport, HTTP 401/503) are transient → §4 retry rule; a `verify-commit` failure is **not retried** (a re-fetch cannot fix an unsigned commit): immediate `failed` report with `revision: null`, `error_summary` = git's last stderr line, nothing applied, working tree unchanged (design §1 says "partial" for a stale signer anchor; `failed` is the right word because nothing ran — §14 aligns the text). **v1.1**: generation-numbered tags `refs/tags/rings/<ring>/N` (agent refuses N < last applied) — additive.
6. ⚙ **Signer rotation, before the play** (design §1): job `{kind:"signers", revision}`. The root side verifies `revision` itself (§10), then reads `git show <revision>:.opale/allowed_signers` (when present), validates it — non-empty after stripping comments/blank lines, every line matches the server grammar `^\S+(\s+[a-z-]+=\S+)*\s+(ssh-ed25519|ssh-rsa|ecdsa-sha2-nistp256|ecdsa-sha2-nistp384|ecdsa-sha2-nistp521|sk-ssh-ed25519@openssh\.com|sk-ecdsa-sha2-nistp256@openssh\.com)\s+[A-Za-z0-9+/]+={0,2}(\s+.*)?$` — and atomically replaces `/var/lib/opale-agent/trust/allowed_signers` (root 0644; `signers-rotated` event, sha256 before/after). Same for `.opale/revoked_signers` (plain public-key lines) → `trust/revoked_signers`. `/etc/opale-agent/{allowed,revoked}_signers` are the image **seed**, copied into `trust/` by `luks-prepare` on first boot and never written again; the daemon has no write access to either location. Invalid file → kept pinned file, `warn` event, cycle continues, report `partial`. Never written from an HTTP response; the assignment has no such field.
7. **Skip rule**: `apply_hash = sha256(revision + "\n" + profile + "\n" + ring + "\n" + canonical JSON(allowlisted extra_vars))`. Skip when `apply_hash == last_success_hash` **and** `now − last_full_apply_at < 24 h`; otherwise run. A failed apply therefore retries every cycle on the same commit, a profile/ring change forces a run, and drift is corrected daily.
8. ⚙ **Play**: job `{kind:"play", profile, ring, revision, extra_vars, first_apply: bool}`. The root side verifies `revision` against `trust/allowed_signers`, exports the tree with `git archive <revision> | tar -x -C $RUNTIME_DIRECTORY/tree` (the daemon-writable checkout is never executed from), writes `$RUNTIME_DIRECTORY/extra_vars.json` (0600) from the job, and runs with `cwd=$RUNTIME_DIRECTORY/tree`, env `ANSIBLE_CONFIG=/etc/opale-agent/ansible.cfg ANSIBLE_HOME=/var/lib/opale-agent/ansible ANSIBLE_NOCOLOR=1 ANSIBLE_FORCE_COLOR=0 ANSIBLE_STDOUT_CALLBACK=ansible.builtin.json ANSIBLE_LOG_PATH=$RUNTIME_DIRECTORY/apply.log` and **no** `GIT_*` / token:
   `ansible-playbook -i localhost, -c local -e @$RUNTIME_DIRECTORY/extra_vars.json profiles/<profile>.yml`.
   **`extra_vars` allowlist** — `-e @file` has the highest variable precedence in Ansible, so a generic pass-through would let whoever controls the check-in response (the server design's residual explicitly includes "the host") override any variable of the signed playbook: sudoers lists, `authorized_keys`, package lists, arguments of `shell` tasks — root through an unsigned channel. The agent forwards **only** `opale_profile` (profile regex), `opale_ring` (enum), `opale_device_id` (uuid), `opale_hostname` (hostname regex), `opale_assigned_user` (`^[A-Za-z0-9@._-]{1,128}$`, §14), and — on the first apply only, generated device-side, never from the server — `opale_initial_password` (§17 Q4). Any other key in the response → `assignment-invalid`, cycle aborted, `failed` report. Adding a key is an agent release. `ansible.cfg` (image): `roles_path`, `collections_path`, `library` restricted to the tree, `interpreter_python=auto_silent`, `retry_files_enabled=False`, `gathering=smart`.
   **Profile contract** (documented, enforced by review): `hosts: localhost`, `connection: local`, vendored `roles/`, `collections/`, `library/` compatible with **ansible-core 2.19** (trixie ships 2.19.x; 2.19 changed templating — data tagging), `no_log: true` on secret-bearing tasks, **no secrets in the fleet repo** (every approved key fetches the whole repo, and approval is automatic for a pre-registered serial — a spoofable SMBIOS string — so the repo is as public as the image: Wi-Fi PSKs, tokens and private keys do not belong there; §17 Q6), never touch `/etc/opale-agent`, `/var/lib/opale-agent`, `/etc/gitconfig` or the agent package except through the documented upgrade task (§11). Mounts performed by a play are ordinary (the apply unit has **no** mount namespace, §10).
9. **Report** (§7), then persist `last_status`, `last_revision`, `last_success_hash` (on success), `last_full_apply_at` (on any run), `first_apply_done`.

**Any cycle that reaches a `200` assignment and does not run the play sends one `failed` report** (`revision: null`, `error_summary` = `<event>: <message>`, `log_tail` = the relevant stderr): `assignment-invalid`, unexpected `git.url`, `verify-commit` failure, invalid signers before a play could run, escrow `400`s, a job refused by the root side, EPERM inside the sandbox. Deduplicated per cause (`last_reported_cause`) the way `skipped` is per hash, so it stays inside the 12/h budget. Rationale: the device has no sshd, no users and an unusable root — `error_summary` is the only diagnostics channel the admin has; an agent that only logs locally is undiagnosable.

## 7. Reports (`linuxAgentReport`)

One `POST /reports` per run (and the `skipped` / abort rules), body `{revision, status, started_at, finished_at, error_summary?, log_tail?, agent_version}`:

- `success`: rc 0 and `stats.localhost.{failures,unreachable} == 0` and `ignored == 0 and rescued == 0` in the JSON callback output. `partial`: rc 0 **and** (`stats.localhost.ignored > 0` or `rescued > 0` — `ignore_errors` increments `ignored`, not `failures`; a non-zero `failures` always yields rc 2, so "rc 0 with failures" is an empty set) **or** a post-step failed (signer file invalid/unwritable, `/etc/hosts` rewrite, TPM re-enrol needed in PIN mode §9). `failed`: rc 2/4/1/250, the play never started (git stage after its retry, `verify-commit`, root-side refusal; `revision: null` when no tree was exported), or the §6 abort rule. `skipped`: skip rule hit, or ansible reports no hosts matched / empty `plays`.
- `error_summary` (≤ 1024, agent-clipped): first task result with `failed == true` → `"<play> / <task>: <msg>"` from the JSON callback; else the git error; else `<event>: <message>`.
- `log_tail`: last 64 KiB of `apply.log` (returned by the root side in the result file, read from its own runtime dir), attached only for `failed | partial` (the server drops it otherwise anyway, `reports.js`).
- `skipped` is sent once per `apply_hash` (`last_reported_hash`), not every 15 min: after a `success`, the next no-op cycle reports `skipped` and the following ones stay silent until something changes or the daily full apply produces a real report. Keeps `devices.last_apply_*` meaningful without 96 rows/day/device.
- `429` on `/reports` → dropped, local state kept; the next run reports afresh. Transition audits (`failed ↔ recovered`) are server-side.

## 8. Local admin (LAPS parity) and escrow (`linuxAgentEscrow`, kind `local_admin`)

Account = `assignment.local_admin_username` (setting `agent.laps_recovery_username`, default `opale-recovery`), validated with the **client-side** regex of §2; refused (`error` event, step disabled, `failed` report once) if it is `root`, a name in the agent's banned list, or an existing user with UID < 1000 that the agent did not create. Triggers: `'local_admin' ∈ escrow_needed`, `rotate_local_admin`, or `state.local_admin.rotated_at` older than 30 days (local LAPS-like policy); only when `escrow.status ∈ {ok, backup_unconfirmed}` (local-admin escrow is not gated by the backup confirmation, design §9.3).

Sequence, escrow-first (the agent never holds a secret the server does not — `agent-go/laps.go:83-139`), **ciphertext-and-hash only on disk** (agent-go's invariant, laps.go:85-89):
1. Password: 32 chars from the Windows charset (no `I l O 0 1`), rejection sampling, must contain lower+upper+digit. `rotated_at = max(now + clock_offset_s, stored rotated_at + 1 s)` (must be > stored `password_changed_at` and ≤ now + 5 min server-side). Ciphertext = base64(RSA-OAEP(SHA-256, MGF1-SHA-256, no label)) under the cycle's PEM (256 B for RSA-2048 → within 200..1024 B). Hash = `openssl passwd -6 -stdin` in the daemon (no home-grown crypt). Stash `/var/lib/opale-agent/stash/local_admin.json` (0600) = `{phase:'prepared', username, hash, ciphertext, rotated_at, key_id}` — **no plaintext**; the plaintext lives in process memory only.
2. `POST /escrow {kind:'local_admin', username, ciphertext, rotated_at, escrow_key_id}`; `201` → phase `escrowed`. `409 ESCROW_STALE` / `ESCROW_KEY_MISMATCH` → stash discarded, regenerated per §4 (never re-sent). The server upserts `device_admin_credentials`, clears `rotation_requested_at`, audits `laps_rotated` by `device:<fp12>`; the admin reveals it through the existing `revealAdminCredential` route with a reason.
3. ⚙ job `{kind:"local_admin", username, password_hash, create: bool}`: `useradd -m -s /bin/bash -G sudo` when absent, `chpasswd -e` on stdin (bypasses pwquality, never argv), `passwd -u`, `/etc/sudoers.d/opale-admin` (`<user> ALL=(ALL:ALL) ALL`, 0440, `visudo -cf` before `mv`), `/var/lib/AccountsService/users/<user>` with `SystemAccount=true` (hidden from the greeter).
4. Success → `state.local_admin = {rotated_at, key_id}`, stash unlinked (not "shredded": `shred` is ineffective on SSD/journaled ext4; the file never held plaintext, so unlink is enough); both values go into the next check-in. Crash between 2 and 3 → the stash in phase `escrowed` is applied on the next start (the server already has it, the job only needs the hash); crash between 1 and 2 → discarded.

## 9. LUKS: install-time bootstrap, first boot, TPM2, recovery key

**Hardware requirements (install-time, enforced)**: TPM 2.0 (`/dev/tpmrm0`) **and** UEFI Secure Boot **enabled**. `early_command` checks both (`/sys/firmware/efi/efivars/SecureBoot-8be4df61-…`, last byte `== 1`) and aborts the install with an on-screen message otherwise. Rationale: with Secure Boot off, PCR 7 has the same value for the installed OS and for any live USB, so a PCR 7 policy would unlock the disk for anyone; and a no-TPM device would need either a plaintext keyfile in the initrd (no encryption) or a passphrase nobody knows until the recovery key is escrowed (bricked by any reboot). There is no "no-TPM mode" (§17 Q2). INSTALL §9.1 lists both requirements.

**Install (`late_command`, §12)**: d-i's `partman-auto/method crypto` writes `/etc/crypttab` with `none` as key, i.e. an initrd passphrase prompt — and the only copy of the per-install passphrase would be inside the volume it unlocks. So `late_command` creates a **bootstrap keyfile** `/target/etc/luks/boot.key` (0400 root, 64 random bytes), adds it as a keyslot using the installer passphrase (read from the file `early_command` left on the installer ramdisk, §12), points `/etc/crypttab` at it (`root UUID=… /etc/luks/boot.key luks,discard`), switches to dracut (`in-target apt-get install -y dracut`, which replaces `initramfs-tools`), adds `install_items+=" /etc/luks/boot.key "` to `/etc/dracut.conf.d/opale.conf` and rebuilds the initrd (`in-target dracut -f`). The installer passphrase slot is removed in `late_command` (it is unknown to everyone). **Documented window**: between the end of the install and the first boot, the disk is unlockable by anyone holding the device (the key is in the clear-text `/boot`); the image is for imaging rooms, and `luks-prepare` closes the window at first boot.

**First boot, before OOBE** — `opale-linux-luks-prepare.service` (root, `Type=oneshot`, `ConditionPathExists=!/var/lib/opale-agent/luks-prepared`, `Before=opale-linux-oobe.service`, runs `opale-linux-agent luks-prepare`): (a) seeds `/var/lib/opale-agent/trust/` from `/etc/opale-agent` (§6.6); (b) creates the agent-owned unlock keyfile `/etc/luks/root.key` (0400 root, 64 random bytes — the credential every later slot change uses, readable only once the disk is open) and adds it as a keyslot with `--key-file /etc/luks/boot.key`; (c) re-checks Secure Boot and the TPM (`tpm-enroll-skipped` event and **retry at every boot** if either is missing — the bootstrap slot is then kept, and the first report carries the cause), then `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 --unlock-key-file=/etc/luks/root.key <luks dev>` (PIN handling per Q2, below), records `tpm2_pcrread sha256:7` in `state.luks.pcr7`, rewrites `/etc/crypttab` to `root UUID=… none luks,discard,tpm2-device=auto`, removes `install_items` for `boot.key`, `dracut -f`; (d) `luksKillSlot` of the bootstrap slot, `boot.key` unlinked; writes `luks-prepared`. From this point the unlock paths are the TPM2 token and `root.key` (inside the volume) until the recovery key exists.

**Boot-chain hardening (image, unconditional)**: `GRUB_DISABLE_RECOVERY=true`, a grub superuser with a random per-install password and `--unrestricted` menu entries (no interactive edit without the password), kernel cmdline `rd.shell=0 rd.emergency=reboot`, `plymouth` quiet. **What this does not do**: d-i leaves `/boot` (kernel, initrd, `grub.cfg`) unencrypted, PCR 7 measures only the Secure Boot policy and the certificates that verified shim/grub, and grub measures the kernel command line and loaded files into PCR 8/9, which are **not** in the policy. A thief who edits `grub.cfg` offline (`init=/bin/sh`, `systemd.debug-shell=1`) keeps PCR 7 intact, the TPM unseals, and a PIN-less device reveals everything, including `root.key` and the device key. This is **not** BitLocker-equivalent (BitLocker binds PCR 11 / boot configuration); it is what Q2 decides.

**TPM PIN (Q2, recommended default for laptops)**: `luks-prepare` enrols **without** PIN at first boot (so a reboot during the OOBE hold works), and the first apply's `luks_prepare` job re-enrols with `--wipe-slot=tpm2 --tpm2-with-pin=yes` and a device-generated 8-digit PIN passed through `$NEWPIN`, shown **once** on the OOBE page after the `success` report (same channel as the initial password, §17 Q4). Opale never stores the PIN. The user changes it with `opale-linux-agent luks-pin` (PR 6: `pkexec`-gated helper, polkit rule for the active local session, re-enrols with the user's new PIN using `root.key`). Rebinding after a PCR 7 change in PIN mode needs the user (the agent cannot re-enrol without the PIN): the agent detects the drift (below), reports `partial` with `error_summary: tpm2 slot stale — run « Définir le code de démarrage »`, and the user runs the helper after unlocking with the recovery key. In PCR 7-only mode (per-profile option for desktops in locked rooms) the re-enrol is automatic.

**PCR 7 drift (both modes)**: every cycle compares `tpm2_pcrread sha256:7` (root side) with `state.luks.pcr7`, and checks `cryptsetup luksDump` still lists a `systemd-tpm2` token; on drift (dbx/fwupd update, Secure Boot toggle, firmware reset) the `luks_prepare` job runs `systemd-cryptenroll --wipe-slot=tpm2 --tpm2-device=auto --tpm2-pcrs=7 --unlock-key-file=/etc/luks/root.key` (PCR 7-only mode) or raises the `partial` above (PIN mode). Without this, every boot after a firmware update would need the admin-revealed recovery key.

**Escrow** (`linuxAgentEscrow`, kind `luks_recovery`) runs in the cycle only when `luks_root && escrow.status == 'ok' && 'luks_recovery' ∈ escrow_needed` — gated on `status`, because `buildAssignment` lists `luks_recovery` even while `backup_unconfirmed` (`checkin.js:43-49`); while unconfirmed nothing is attempted, `status` prints « escrow LUKS en attente de confirmation de sauvegarde », and the OOBE page refuses to show « Poste prêt » (§3.4). **Residual, documented**: between first boot and the first successful escrow, a PCR 7 change (or a TPM failure) leaves no human-known unlock path; INSTALL §9.1 therefore requires the `laps.key` backup confirmation **before the first device is imaged**, and the device page's "non escrowé" filter (design §4) shows devices still in that window.
1. Recovery key = 48 Crockford-base32 chars in 6 groups of 8 separated by `-` (53 B ≤ 150, typeable at the initrd prompt; the passphrase is the literal string with dashes). Stash `stash/luks.json` phase `prepared` = `{ciphertext, key_id, passphrase}` — the plaintext **is** on disk here, 0600, inside the LUKS volume it protects, for the seconds between escrow and slot add (there is no hash equivalent for a LUKS passphrase); stated explicitly, and unlinked (not "shredded") afterwards.
2. `POST /escrow {kind:'luks_recovery', label:'/', ciphertext, escrow_key_id}` — label `/` so each rotation supersedes the previous row server-side (history kept, `escrow.js:72-98`), no slot bookkeeping in the label. `201` → phase `escrowed`.
3. ⚙ job `{kind:"luks_escrow", passphrase}` (job file 0640 in the daemon's tmpfs, unlinked by the root side on read): `cryptsetup luksAddKey --key-file /etc/luks/root.key --new-keyfile <fd> --batch-mode <dev>`, new slot read from `luksDump`, the previous recovery slot (`state.luks.slot`) killed with `luksKillSlot --key-file /etc/luks/root.key`, `state.luks = {slot, key_id, escrowed: true}`, stash unlinked. Crash recovery: phase `escrowed` → `cryptsetup open --test-passphrase` with the stash decides whether the slot already exists. `ESCROW_KEY_MISMATCH` (server key rotated) → a brand-new key; plaintext is never retained. The admin reveals it through `linuxRevealRecoveryKey` (fail-closed audit).

## 10. Privilege split and hardening

**Units** (all shipped by the `.deb`, `systemd-analyze verify --root=<staging>` in CI):

- `opale-linux-luks-prepare.service` — root, oneshot, §9. Executes `cryptsetup`, `systemd-cryptenroll`, `tpm2_pcrread`, `dracut`.
- `opale-linux-oobe.service` — `User=opale-agent`, oneshot, tty1, §3. Same sandbox as the daemon; `ExecStartPre=+` lines for `plymouth quit` and `cache-facts`.
- `opale-linux-agent.service` — `User=opale-agent`, `Group=opale-agent`, `Type=notify`, `After=opale-linux-oobe.service network-online.target`, `Wants=opale-linux-oobe.service`, `ConditionPathExists=!/var/lib/opale-agent/revoked`, `ConditionPathExists=!…/rejected`, `ConditionPathExists=!…/serial_mismatch`, `StateDirectory=opale-agent` (0700), `RuntimeDirectory=opale-linux-agent` (tmpfs, 0700: response bodies, job files, progress files), `ExecStartPre=+/usr/bin/opale-linux-agent cache-facts` (root, reads the 0400 DMI serial into `facts.json` once), `ProtectSystem=strict` (no `ReadWritePaths`: the two directories above are the only writable paths), `PrivateTmp=yes`, `ProtectHome=yes`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectControlGroups=yes`, `ProtectClock=yes`, `RestrictNamespaces=yes`, `RestrictSUIDSGID=yes`, `LockPersonality=yes`, `MemoryDenyWriteExecute=yes`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, `SystemCallFilter=@system-service`, `CapabilityBoundingSet=` (empty), `NoNewPrivileges=yes`, `DevicePolicy=closed` (PR 6: `SupplementaryGroups=tss` + `DeviceAllow=/dev/tpmrm0 rw`), `WatchdogSec=5min`, `Restart=on-failure`, `RestartSec=30`, `RestartForceExitStatus=75`. It executes only `git`, `openssl passwd`, `systemctl start opale-linux-apply@<n>.service` and `systemctl kill` (nudge target is itself). The three reasons the draft gave for `User=root` do not hold: the state dir is owned by the service user, the DMI serial is cached by the root `ExecStartPre=+`, the TPM is group `tss`.
- `opale-linux-apply@.service` — **static template, root**, `Type=oneshot`, `ExecStart=/usr/bin/opale-linux-agent privileged %i`, `RuntimeDirectory=opale-linux-apply/%i` (its own tmpfs: `tree/`, `extra_vars.json`, `apply.log`), `RuntimeMaxSec=1800`, `KillMode=control-group`, `SyslogIdentifier=opale-linux-apply`, `CollectMode=inactive-or-failed`. **No mount-namespacing options** (`InaccessiblePaths=`, `ProtectHome=`, `PrivateTmp=`): they would give the play a private mount namespace with slave propagation, so any mount a profile performs (`ansible.posix.mount`, cifs/nfs shares, `mount -a`) would vanish with the unit while the task reports `changed` — and `ProtectHome=read-only` would break `useradd -m` and the profile's user creation. They were also never a boundary: a root play can `nsenter -t 1 -m`. Secrets are kept from the play by **not giving them to it** (no token, no `GIT_*`, no key in env or argv; the key and stash are `opale-agent`-owned 0600 files that a root play *could* read but has no handle to), not by over-mounts.
- `/usr/share/polkit-1/rules.d/50-opale-linux-agent.rules` — allows `org.freedesktop.systemd1.manage-units` for `opale-agent` only when `action.lookup("verb") == "start"` and `action.lookup("unit")` matches `^opale-linux-apply@[0-9]+\.service$`. Debian 13's polkitd evaluates JS rules. No-polkit fallback if it costs cycles: `opale-linux-apply.path` (`PathExistsGlob=/run/opale-linux-agent/jobs/*.json`) starting a root service that drains the queue — same job/result files, the daemon waits on the result file instead of on `systemctl`.

**The root side (`privileged <n>`)** reads `/run/opale-linux-agent/jobs/<n>.json`, re-validates every field with the same regexes, refuses unknown kinds and unknown `job_version` (one version of backward compatibility, so an old daemon can hand a job to a freshly upgraded binary — §11), builds fixed argv lists (`exec.Command` with literal arguments, never a shell), and writes `<n>.result.json` (`{status, rc, stats, error_summary, log_tail}`) plus task names (never arguments) to `<n>.progress` for the OOBE page and to its journal (`SyslogIdentifier=opale-linux-apply`, so `journalctl -u 'opale-linux-apply@*'` shows what ran — with `systemctl start` there is no `--pipe`, so this is the only trail). Job kinds: `hostname | signers | local_admin | luks_escrow | luks_prepare | gdm_banner | play`. For `signers` and `play` it is the **authority on trust**: it runs `git verify-commit <revision>` against the root-owned `trust/allowed_signers`, exports the tree with `git archive` into its own tmpfs, and executes from there — the daemon's checkout and pre-check exist only to fail early and to compute `revision`. A compromised daemon can therefore choose *which* signed revision and *which* allowlisted variables run (the server-side selection residual, design §1, now also holds for the device), create a user via `opale_assigned_user`/`opale_initial_password` with a profile that honours them, and DoS the device — but cannot run unsigned content, read `/etc/luks/root.key` (root 0400), or rewrite the trust root. A profile itself is unrestricted root on the device — accepted by design: its content is signed by a pinned human key, selected by ring, and the device exposes no other execution surface.

**Fail-closed inventory**: unexpected `git.url`, unverifiable commit (either side), invalid signers file, `ESCROW_KEY_MISMATCH`, assignment regex or allowlist failure, unknown job kind/version, unknown error code → nothing applied, event logged, **`failed` report sent** (§6). A compromised Opale is denial of service plus the selection residual, not root (design §1). **Residuals to state in INSTALL**: (1) pre-registration auto-approve trusts a spoofable SMBIOS serial (`qemu -smbios type=1,serial=…`; serials are on stickers and in the Intune export), so anyone with the ISO and a pre-registered serial obtains the fleet repo, the assigned user's login, the local-admin username and can escrow bogus keys on the real device's row (which later shows as `clone`) — hence "no secrets in the fleet repo" (§6.8) and the advice to disable auto-approve for sensitive profiles; (2) the physical-access attack on clear-text `/boot` for PIN-less devices (§9); (3) the pre-escrow window (§9).

## 11. Updates, logging, support commands

**Updates: apt + the signed commit, no in-band channel** (design §4: "self-update is the image/apt repo's job"). release.yml gains an `nfpm` step producing `opale-linux-agent_<v>_{amd64,arm64}.deb` + sha256 sidecars as unsigned release assets (same policy as the Windows binaries, release.yml:10-20). The fleet repo's base role pins the agent, **downgrade-guarded** (`apt deb:` goes through `dpkg -i`, which installs older versions silently — a stable rollback or an older signed pilot tip would otherwise reinstall known bugs):
```yaml
- ansible.builtin.command: dpkg-query -W -f '${Version}' opale-linux-agent
  register: opale_agent_installed
  changed_when: false
- ansible.builtin.get_url: {url: "https://github.com/…/opale-linux-agent_1.2.0_amd64.deb", dest: /var/cache/opale/agent.deb, checksum: "sha256:<pinned>"}
  when: opale_agent_installed.stdout is version('1.2.0', '<')
- ansible.builtin.apt: {deb: /var/cache/opale/agent.deb}
  when: opale_agent_installed.stdout is version('1.2.0', '<')
```
Integrity = the sha256 in a commit signed by a pinned signer; GitHub is transport only. **Restart without killing the cycle**: the `.deb` is installed *inside* the apply unit while the daemon waits on it, so a restart from `postinst` — even deferred by 5 s — would kill the daemon mid-apply, orphan the unit, lose the report and re-run the whole apply next cycle. `postinst` therefore only runs `daemon-reload` and touches `/run/opale-linux-agent/restart-requested`; the daemon checks the file **after the report step** and exits 75 (`RestartForceExitStatus=75` restarts it on the new binary). `prerm` stops the unit on **remove only**, never on upgrade. The apply unit started by the old daemon may already run the new `privileged` binary: `job_version` with one version of backward compatibility covers the skew. Debian itself updates through `unattended-upgrades` (security pocket) enabled by the image. The device therefore reaches Opale, deb.debian.org and github.com — §17 Q5 if egress must be narrower.

**Logging**: JSON lines on stdout → journald (`SyslogIdentifier=opale-linux-agent`; `event` kebab-case: `enroll-pending`, `enroll-approved`, `checkin-ok`, `assignment-invalid`, `git-fetch-failed`, `verify-failed`, `signers-rotated`, `apply-start`, `apply-done`, `report-sent`, `escrow-ok`, `tpm-enroll-skipped`, `tpm-pcr-drift`, `halted`, `revoked`). A static test asserts no log call site carries a field named `token|password|passphrase|pin|ciphertext|key|pem` and no `%v` of a struct holding one. `opale-linux-agent status` prints state, code, device_id, hostname, last report, next run, `not_before`, clock offset, signers sha256, escrow states (local admin, LUKS, TPM mode and PCR 7 status), the check-in window usage, and a check that `OPALE_URL` matches the last `git.url` seen (the FRONTEND_URL trap). `opale-linux-agent reset` (root) wipes key, state, markers — the documented support path after a revoke, reject or serial mismatch (the device then re-enters the queue with a new key, as `reimage` if its row exists, approved with `supersede`).

## 12. Image pipeline (`agent-linux/image/`)

`build-iso.sh --inputs <dir>` runs in a `debian:trixie` container with `xorriso`, `cpio`, `isolinux`/`grub-efi` files from the netinst: download the **pinned** trixie netinst (point-release version and sha256 committed in `image/netinst.lock`, fetched from the `cdimage/archive/` URL so the next point release does not break the build; cached in CI), `validate-inputs.sh` (https URL, `ca.pem` parses, `allowed_signers` non-empty and every line matches the grammar, `.deb` present and `dpkg-deb -I` sane, pin hex when set, lab-only flags refused outside CI), render `preseed.cfg` from the template, inject it into `initrd.gz` (cpio append), add `/opale/` on the ISO (the `.deb`, `agent.conf`, `ca.pem`, `allowed_signers`, `revoked_signers`, `gitconfig`, `ansible.cfg`), **patch both boot menus** (`boot/grub/grub.cfg` and `isolinux/txt.cfg`: default entry, `timeout=5`, `auto=true priority=critical` — injecting the preseed alone still stops at the menu; `smoke.sh` asserts the strings), rebuild with xorriso keeping the UEFI El Torito image (Secure Boot via `shim-signed` / `grub-efi-amd64-signed`, in-tree drivers only). Inputs live in gitignored `instance-local/linux-image/`; output `opale-<instance>-<date>.iso` + sha256. Rebuild when the CA or the signers rotate (INSTALL §9.2). Package versions are those of the mirror on the day of the install (netinst pulls from deb.debian.org); pin `mirror/http/hostname` to a snapshot.debian.org date if two installs a month apart must be identical.

Preseed: `partman-auto/method crypto` (LVM-on-LUKS, LUKS2), `partman-auto-crypto/erase_disks false`. **`early_command`**: abort unless `/dev/tpmrm0` exists and Secure Boot is enabled (§9); generate the LUKS passphrase into `/var/run/opale-luks.key` (0600, installer ramdisk) and preseed **both** `partman-crypto/passphrase` and `partman-crypto/passphrase-again` with `echo … | debconf-set-selections` (marks them seen; `debconf-set` alone does not, and d-i is not guaranteed to retain the value for a later `debconf-get` — this path does not depend on it); generate the root hash (`passwd/root-password-crypted`, §3) and the grub superuser password the same way. `passwd/root-login true`, `passwd/make-user false`. `pkgsel/include`: `git ansible-core openssh-client systemd-timesyncd sudo cryptsetup-bin systemd-cryptsetup tpm2-tools libtss2-* plymouth gdm3 gnome-core unattended-upgrades` (no `openssh-server`: outbound only; **not** `dracut` here — the switch is explicit in `late_command`). **`late_command`**: `cp /cdrom/opale/*.deb /target/tmp/ && in-target apt-get install -y /tmp/opale-linux-agent_*.deb` (the ISO is at `/cdrom`, the target at `/target`; `dpkg -i` would not resolve dependencies), copy `/cdrom/opale/{agent.conf,ca.pem,allowed_signers,revoked_signers,gitconfig,ansible.cfg}` → `/target/etc/opale-agent/`, the LUKS bootstrap of §9 (keyfile, slot, crypttab, dracut, initrd, installer slot removed), grub hardening of §9, hostname placeholder `opale-pending`, enable the units, `InitialSetupEnable=false`, hide `gnome-initial-setup-first-login.desktop` and `gnome-tour`, `rm -rf /target/var/log/installer /target/etc/NetworkManager/system-connections/*` (no Wi-Fi PSK in the image: imaging over Ethernet/dock), keep `/var/lib/systemd/timesync/clock` (first TLS handshake never sees "certificate not yet valid"). Baked by design: URL, CA/pin, public signers, the agent. Absent: tokens, signing keys, the escrow private key, a device key, a Wi-Fi secret. Because d-i installs per device there is no golden-image strip list; `strip.sh` exists only for the lab QEMU snapshot. Lab-only (dummy inputs, refused by `validate-inputs.sh` otherwise): `console=ttyS0` + `serial-getty@ttyS0` with root autologin, for the VM smoke's journal access.

Deployment prerequisites to state in INSTALL §9 (PR 5): the reverse proxy must pass `/api/linux/agent/*` **unmodified** (the signed target is `req.raw.url`, `plugins/device-auth.js:23`); `FRONTEND_URL` must equal the baked `OPALE_URL` byte for byte after trailing-slash stripping (`checkin.js:15-21`), or every device refuses `git.url`; `client_max_body_size 8m` and `proxy_read_timeout 300s` on `/api/linux/agent/git/`; confirm the `laps.key` backup **before imaging the first device** (§9).

## 15. Decisions

Decided here (say so if you disagree):
- **Go, separate module `agent-linux/`.** Rejected: a second `main` in `agent-go` (drags conpty/wmi/websocket and Windows branding; legacy UA classification); bash (1 500 lines moving passwords, LUKS passphrases and bearer tokens through argv/env — `openssl passwd -6 "$pw"` already leaks via `/proc`; review discipline as the only control); Python (third language, 3.11/3.13 matrix, no SPKI pin on the verified chain, its apt-on-gh-pages plan adds a central signing key in GitHub Secrets, contrary to the release policy).
- **Daemon over timer+oneshot.** Rejected the timer because `checkin_interval_s` is server-driven (volatile drop-ins + `daemon-reload` to honour it), enrol polling needs its own loop anyway, and backoff/nudges live naturally in a scheduler. The design §1 guarantee is preserved (`exit 0` + `ConditionPathExists`). If the daemon sandbox eats debugging cycles in PR 3, the fallback is the timer model with the same code (`run --once`), not a rewrite.
- **Unprivileged daemon + static root template unit, root side re-verifies and exports the tree.** Rejected `User=root` + `systemd-run` (PID 1 authorises by uid; `CapabilityBoundingSet=`/seccomp do not propagate into the transient unit; a daemon RCE was root on the whole disk — the draft's containment claim was false). Rejected a root side that runs from the daemon's checkout (TOCTOU: the daemon could rewrite the tree after its own verification). Polkit rule scoped to the unit prefix; `.path` unit as the no-polkit fallback.
- **`extra_vars` allowlist over generic pass-through.** `-e @file` is top precedence; a generic pass-through made the check-in response a root channel. Adding a variable is an agent release.
- **Agent-driven git + `ansible-playbook` over literal `ansible-pull`.** Rejected ansible-pull because `--verify-commit` runs after the fetch inside the git module, git-stage vs play failures are only distinguishable by parsing output, and `--only-if-changed` hides repeated failures and never corrects drift.
- **`.deb` pinned by sha256 in the signed fleet commit, downgrade-guarded, restart requested after the report** over in-binary ed25519 self-update, an Opale-hosted apt repo or a gh-pages apt repo. No new server route, no central key, no second trust root; the price is that an agent upgrade is a reviewed commit and a rollback is another commit. Rejected committing the binary itself to the fleet repo (5 MB per arch per version in git).
- **Debian 13 + preseeded d-i over Debian 12 or a golden image** (live-build/FAI/mkosi): per-device LUKS master key, native `systemd-cryptsetup`, ansible-core 2.19, no strip list; bookworm would force clevis or dracut backports and ansible-core 2.14.
- **TPM 2.0 + Secure Boot as hard install-time requirements; no no-TPM mode.** A no-TPM device has no human-known unlock path until escrow (bricked by any reboot) or a plaintext keyfile in the initrd (no encryption); Secure Boot off makes PCR 7 unlock for any medium.
- **Bootstrap keyfile in the initrd between install and first boot** over TPM enrolment in `late_command` (PCR 7 in the installer environment can differ from the installed boot chain) or an installer passphrase prompt (nobody knows it). The window is documented and closed by `luks-prepare`.
- **dracut + `systemd-cryptenroll` PCR 7 (+ PIN by default for laptops) over clevis**: same path serves the PIN; clevis has no PIN support and a second tooling stack. Switch to dracut done explicitly in `late_command`, not via `pkgsel/include`.
- **tty1 OOBE page with bounded hold + GDM banner fallback** over plymouth-only messages (theme-dependent rendering, no status line), an infinite boot hold (strands devices when Opale is unreachable), a kiosk session (most code), and gnome-initial-setup (replaces the greeter, user picks their own name, Opale learns the user only afterwards).
- **Profile-created end user** over gnome-initial-setup: Autopilot-like, deterministic, but needs `opale_assigned_user` (§14) and the first-apply `opale_initial_password` (§17 Q4).
- **Local-admin password hashed with `openssl passwd -6` in the daemon** over a Go sha512crypt/yescrypt implementation: one exec, zero home-grown crypto; the hash, never the password, crosses the job boundary or touches disk.
- **LUKS label `/`** over `<dev>:slot<N>`: rotation = server-side supersede, no agent bookkeeping in the label; only the root volume is escrowed in v1.
- **`rejected` / `serial_mismatch` terminal like `revoked`** (reversed from the draft's hourly re-poll): the server has no path back from either state, so the poll would have burned requests forever; the real support path is `reset` → `reimage` → `supersede`.
- **CA file as the primary TLS anchor, SPKI pin optional and API-only**: one file serves the agent and git; the pin (on the verified chain, never replacing CA validation) is for instances that want it. git is not pinned (leaf-only semantics of `pinnedPubkey`). Rejected build-time embedded pins.
- **`skipped` reported once per hash, `failed` once per cause** rather than every cycle (row volume) or never (the server would lose `last_apply_at` freshness and the admin would have no trace of agent-side aborts).

## 17. Open questions for the user

1. **Image base: Debian 13 (trixie) rather than 12?** It drives TPM2 unlock (native `systemd-cryptsetup`), ansible-core 2.19 for vendored collections, and `systemd-cryptenroll` features. *Recommended: Debian 13; add bookworm devices only if a concrete need appears (they would need clevis and a 2.14-compatible fleet repo).*
2. **TPM2 policy: PCR 7 + PIN (default for laptops) or PCR 7 only?** The trade-off, honestly: `/boot` is clear-text under d-i, so a PIN-less device is fully readable by anyone who edits `grub.cfg` offline and boots it — the grub password and `rd.shell=0` stop the casual case, not the offline one; this is **not** BitLocker-equivalent. PIN mode closes it at the cost of a code typed at every boot, a device-generated initial PIN shown once at OOBE, a helper to change it, and a user-driven re-enrol after firmware updates that move PCR 7 (automatic in PIN-less mode). Measured-boot alternatives (PCR 7+8+9 with a kernel-postinst hook, or UKI + PCR 11) are not available from d-i without a second boot per kernel update. TPM 2.0 and Secure Boot are hard requirements either way (no no-TPM mode). *Recommended: PIN by default, PCR 7-only as a per-profile option for desktops in locked rooms; documented in INSTALL §9.1.*
3. **OOBE hold: 30 min on the tty page, then release to a user-less greeter with the code as banner?** The alternative (hold until approved) mirrors Autopilot but strands devices when Opale is unreachable. *Recommended: bounded 30 min; support knows the code is in `/var/lib/opale-agent/enroll-code` and in `status`.*
4. **End-user account from the pre-registration (profile-created via `opale_assigned_user`) rather than gnome-initial-setup, with the initial password generated on the device and shown once on the OOBE page?** Mechanism: for the first apply only, the agent adds `opale_initial_password` to the allowlisted extra_vars (root side's tmpfs, 0600); the profile uses `password: "{{ opale_initial_password | password_hash('sha512') }}"`, `update_password: on_create`, `no_log: true`; the OOBE page prints the value (and the TPM PIN in PIN mode) after the `success` report; the person holding the laptop types it and changes it at first login (`chage -d 0` by the profile). Opale never sees it. Alternatives: admin-revealed one-time password (a new escrow kind and route), help-desk ticket. *Recommended: device-generated, shown once.*
5. **Agent delivery and egress: `.deb` fetched from GitHub Releases with a sha256 pinned in the signed commit (devices reach github.com and deb.debian.org besides Opale)?** The stricter alternative is an apt cache/proxy or hosting the `.deb` behind Opale (a new server route). *Recommended: GitHub transport for v1; revisit with an apt proxy only if the network policy restricts egress.*
6. **Imaging over Ethernet/dock only, and Wi-Fi via 802.1X/EAP-TLS or a user-typed PSK — never a PSK in the fleet repo?** The repo is readable by any approved key, and a pre-registered serial auto-approves (§10 residual), so a PSK in a profile is a PSK in the image. Options: EAP-TLS on per-device certificates issued by a profile task (the profile can enrol against an internal CA reachable from the LAN), or the user types the PSK once in GNOME. *Recommended: Ethernet-only for imaging; EAP-TLS where the infrastructure exists, user-typed PSK otherwise; disable pre-registration auto-approve for profiles that handle sensitive data.*
