# Opale — Linux fleet management (pull-based): design

Status: v2 (2026-09-30). Reviewed adversarially (4 lenses + 2 refuters per finding; 18 findings folded in, 8 refuted) plus a dedicated git-mirror review. Source of truth for the server side alongside `api/modules/linux/openapi.yaml`; the agent / ISO repo implements the agent contract described in §1, §3 and §4.

Goal (user): Opale is the server a custom Debian ISO pulls its goal state from — "bake ansible-pull into Opale" — with a clean OOBE, so users can be moved from Windows to Linux progressively.

## 0. Summary of what changes vs the draft plan, and why

| Draft plan | Reality in the repo | v2 |
|---|---|---|
| "client cert or signed key" | API listens plain HTTP behind the reverse proxy; never sees the TLS handshake (api/index.js:95). | **Ed25519 device keypair, signed requests.** The key *is* the credential; approval is a state flip; nothing secret to deliver or store server-side. |
| "registry extended … status pending/approved/revoked" | `devices.hostname` NOT NULL UNIQUE (001_init.sql:15); every KPI/alert/deploy query reads `devices` unfiltered. | Enrolment requests live in `linux_device_keys`; only **approved** machines become `devices` rows, tagged server-side `managed_by='pull'`. |
| "Git repo URL, branch per ring, signing fingerprint" served by Opale | (user decision) | **Opale mirrors the fleet repo and serves it read-only over git smart HTTP**; revision pinned per ring; **the trust root (allowed signers) is on the device, never served** (see §1). |
| "no arbitrary command on Linux" | 7 server paths can run code on any `devices` row; the legacy `/checkin` response is a command queue; legacy tokens can *claim* rows by serial. | New agent only speaks `/api/linux/agent/*` with its own credential; legacy ingress (`checkDeviceClaim`, `authToken`) refuses pull rows; admin set-operations *filter* pull rows, single-target operations *refuse*. |
| "every apply result → audit log" | Per-checkin audit rows were removed for volume (agent.js:1342); logAudit is fail-open. | Reports in their own table (90 d, no log on success); audit only transitions. |
| "least privilege on roles" | One boolean `is_admin`; non-admins locked out of the UI; CLI tokens = full admin for 90 d. | v1: admin-only + `requireInteractive` (CLI tokens refused on approve/revoke/settings/promote/reveal) + mandatory reason + fail-closed audit on secret reads. | "same model as LAPS" | Reusable server-side, but: one row/device, rotate flag never consumed, `laps.pub` is baked into the image and is *not* what the API uses. | Public key **derived from `laps.key` at runtime**; LUKS keys in their own table with history; rotate flag consumed by the Linux check-in. |
| "OpenAPI first, source of truth" | No tooling; Fastify 5 = Ajv draft-07 strict; `docs/` is not in the Docker image. | Spec written **first**, as YAML under `api/modules/linux/openapi.yaml` (in the image), draft-07-strict subset; routes take their `schema` from it via a 10-line dereferencer; a test boots the module (catches unknown keywords) and asserts operation parity. |
| "separate repo for the client agent" | agent-go compiles on Linux but: `package main`, hardened unit incompatible with ansible-pull, static token, command/console protocol, would be **offered the Windows .exe as self-update** (agent.js:32-48, 1306). | Separate thin agent (copy portable pieces). Server fix now: never offer `agent_update` to a non-Windows User-Agent. |

Latent bugs fixed on the way (PR 0): agent_update offered by arch only; `PATCH /api/settings` unaudited; 429 body loses `retry_after_ms`; CONFIGURATION.md says `agent_offline_days` default 2 (code 7) and "ed25519 over SHA-256" (code: raw bytes). Migration-dependent fix (PR 1a): the Intune upsert overwrites a re-imaged laptop back to Windows on every sync (settings.js:364-383) — both `ON CONFLICT` clauses skip `managed_by='pull'`.

## 1. Identity, credential, trust roots

**Device key.** First boot: the agent generates an Ed25519 keypair (`/var/lib/opale-agent/key`, 0600 root) and records `/etc/machine-id` next to it; if the machine-id differs later (cloned image), it regenerates and re-enrols. Image build must strip `/var/lib/opale-agent` and `/etc/machine-id` (same class as SSH host keys). TPM sealing is an agent-side upgrade; server only stores `key_backing ∈ {software, tpm}`.

**Identity** = `key_fingerprint` = sha256(raw 32-byte public key), hex. Serial and hostname are *claims*: serial is checked at enrolment against pre-registrations and existing rows, and re-checked on every check-in (accidental-clone detection); hostname is never used as identity and never written to `devices` from the agent.

**Signed requests** (all `/api/linux/agent/*` except the git smart-HTTP routes):
```
X-Opale-Key: <fingerprint>        X-Opale-Timestamp: <unix s>
X-Opale-Nonce: <16 bytes hex>     X-Opale-Signature: base64(Ed25519(priv, canonical))
canonical = "opale-linux-v1\n" + METHOD + "\n" + path_with_query + "\n" + timestamp + "\n" + nonce + "\n" + sha256hex(raw_body)
```
Server (`api/modules/linux/lib/device-auth.js`, pure `verify({method, url, headers, rawBody, now, lookupKey, nonceSeen})`, unit-tested):
1. key row by fingerprint; status must be `approved` except on `/enroll` (any status; the response tells the agent what it is).
2. `|now − timestamp| ≤ 300 s`, else `401 {code:'CLOCK_SKEW', server_time}` — fresh installs without NTP (RTC left in local time by Windows) read the offset from the body and retry.
3. nonce unseen in the last 10 min (in-RAM Map, TTL, capped at 50k entries — same posture as `one-shot-grant`; a restart opens a 10-min replay window for traffic that TLS already protects; accepted). A monotonic per-key timestamp column was considered and rejected: a backwards NTP step would lock the device out until its clock catches up.
4. `crypto.verify(null, canonical, publicKey, signature)`.
Raw body: the linux agent plugin registers `addContentTypeParser('application/json', {parseAs:'buffer'})` and keeps the buffer on `req.rawBody`, then JSON-parses; Fastify schema validation still applies. Auth runs as a `preValidation` hook so garbage bodies get 401 before 400.

**Rate limits**: plugin limits on agent routes are IP-only (`ipOnlyKey`) — never a composite `ip|fingerprint` key (rate-limit.js:59-60 trap). Per-device limits are enforced in handlers after verification (SQL count or a small RAM map). Product-wide (not this module): boot-time warn when `NODE_ENV=production` and `TRUST_PROXY` is empty; `landing/install.sh` writes `TRUST_PROXY=uniquelocal` + loopback-only port binding (it already requires the proxy).

**Revocation**: `status='revoked'` on the key row; every later signed request gets `401 {code:'REVOKED'}` (rate-limited 2/min per fingerprint); the agent persists a `revoked` marker and stops (timer unit, exit 0 — no crash loop). Re-enrolment needs a new key; the old fingerprint stays revoked. `DELETE /api/devices/:id` is erasure (cascade, PRIVACY §5): a still-running agent re-enters the queue once as pending — reject it.

**Trust root for code** — the part that makes "Git-only, no arbitrary command" true *by construction* (verified with real git: a commit signed by a non-listed key fails `verify-commit`; rewriting the signers file from the server would have made it pass):
- `/etc/opale-agent/allowed_signers` (SSH signature format, `principal ssh-ed25519 AAAA…`) is installed by the image and **never written from a server response**. Opale does not send signers to devices; the check-in schema has no such field.
- Rotation in-band: the fleet repo carries `.opale/allowed_signers`; after `--verify-commit` passes against the *currently pinned* set, the agent reads `<ring>:.opale/allowed_signers`, validates it (non-empty, every non-comment line parses as `principal [options] <keytype> <base64>`), and atomically replaces the pinned file. A new key can only be introduced by a commit signed with an existing one. v1 accepts the stale-anchor limitation (a device imaged before a rotation fails closed with a clear `partial` report; rebuild the image when signers rotate); the bounded `git log --reverse -- .opale/allowed_signers` chain-walk is a follow-up.
- Opale's own TLS identity is pinned in the image (the proxy's CA or SPKI, applied to the agent HTTP client and to git via `http.sslCAInfo`) — no trust-on-first-use on an imaging network.
- The git URL the agent pulls from is derived from its configured server URL (`<server>/api/linux/agent/git/fleet.git`); the check-in response's `git.url` must equal it or the agent refuses.
- **Residual, documented**: Opale (any admin, a leaked CLI token, the host) is the *selection* authority — it chooses which signed commit each ring/device applies, including an older signed one or one from an unmerged branch — but cannot make devices apply unsigned or attacker-signed content: a compromised Opale degrades to denial of service, not root. Server-side hygiene against honest mistakes: promote requires the commit to be an ancestor of the ring's upstream branch, and promoting an ancestor of the current stable requires `allow_rollback:true` (audited). Attacker-proof selection (generation-numbered signed tags `refs/tags/rings/<ring>/N` created by a signing human, agent refuses N < last applied) is additive on this layout and is the v1.1 path if promotion must not remain a keyless UI click. Windows admins today have root on the whole Windows fleet via scripts/deploy/self-update; Linux is strictly narrower.

## 2. Data model (migration 080; every new table listed in `scripts/migrate-instance/tables.js`, PRIVACY.md §2/§4 updated)

```
linux_device_keys                     -- enrolment requests + live credentials, one row per key
  id UUID PK, device_id UUID NULL REFERENCES devices(id) ON DELETE CASCADE,
  key_fingerprint TEXT UNIQUE, public_key BYTEA, key_backing TEXT CHECK ('software','tpm'),
  serial_claimed TEXT (normalized via device-claim.js normalizeSerial; NULL for FAKE_SERIALS),
  hostname_claimed TEXT (display only), os_version TEXT, agent_version TEXT,
  status TEXT CHECK ('pending','approved','rejected','revoked'),
  source TEXT CHECK ('manual','preregistration'), conflict JSONB NULL ({device_id|key_id, kind}),
  first_seen_at, last_seen_at, enroll_attempts INT,
  approved_at, approved_by, rejected_at, rejected_by, revoked_at, revoked_by, revoke_reason
  UNIQUE INDEX (device_id) WHERE status='approved'      -- one live credential per device
  RETENTION: status='pending' AND last_seen_at < now()-7d (RETENTION_RULES gains an optional `where`)
linux_preregistrations
  id, serial TEXT UNIQUE (normalized; FAKE_SERIALS rejected at import), hostname TEXT UNIQUE NULL (RFC-1123 label, checked against devices.hostname),
  profile TEXT, ring TEXT CHECK ('pilot','stable'), assigned_user_id TEXT NULL (resolved from email at import, LOWER(email) match like match-sender.js),
  note, created_by, created_at, consumed_at, consumed_by_key_id
linux_apply_reports                   -- append-only, one row per run; RETENTION 90 d
  id, device_id FK CASCADE, revision TEXT (40-hex) NULL, status CHECK ('success','failed','partial','skipped'),

device_recovery_keys                  -- LUKS / TPM escrow, history kept
  id, device_id FK CASCADE, kind CHECK ('luks_recovery','tpm_owner'), label TEXT (volume/keyslot),
  ciphertext BYTEA, key_id TEXT (sha256 of the escrow SPKI DER), created_at, superseded_at, last_viewed_at, last_viewed_by
devices (ALTER, additive, no backfill ⇒ trivially replay-safe)
  platform TEXT CHECK ('windows','linux','macos') NULL,      -- set to 'linux' at approval; NULL = legacy/unknown
  managed_by TEXT CHECK ('pull') NULL,                       -- server-set, only for pull-managed rows
  profile TEXT NULL, ring TEXT CHECK ('pilot','stable') NULL,
  last_revision_applied TEXT, last_successful_revision TEXT, last_apply_status TEXT, last_apply_at TIMESTAMPTZ
settings (seeded ON CONFLICT DO NOTHING)
  linux.repo_url                   upstream, https:// ONLY in v1 (credential: env LINUX_GIT_TOKEN + LINUX_GIT_USER, injected per command
                                   through a credential helper reading the env — never in the URL, never in the mirror's config; userinfo stripped from status/errors)
  linux.ring.pilot                 JSON {"branch":"main"}          -- pilot follows the upstream branch tip (auto-advanced by the fetch worker)
  linux.ring.stable                JSON {"branch":"main"}          -- stable moves only by promote
  linux.allowed_signers            JSON array of allowed_signers lines — SERVER-SIDE ONLY (pilot advancement guard, promote guard, "signed" badge);
                                   materialised to $LINUX_GIT_DIR/allowed_signers; NEVER sent to devices
  linux.alerts_enabled             'false'

```
Profiles are **not** a table or a setting: a profile is `profiles/<slug>.yml` in the fleet repo. The UI lists `git ls-tree` of `profiles/` at each ring's tip; assignment accepts `^[a-z0-9][a-z0-9-]{0,63}$` and the list/detail show a warning badge when the slug is absent from the mirror.

**Git mirror** (`api/modules/linux/lib/git-mirror.js`, reviewed separately — the shape survived, the details changed):
- Layout: `git init --bare $LINUX_GIT_DIR/fleet.git`; `remote.upstream.fetch = +refs/heads/*:refs/remotes/upstream/*` and `+refs/tags/*:refs/tags/*`; worker `git fetch --prune upstream` every 5 min (`--prune` then only touches `refs/remotes/upstream/*`). **Rings are Opale-owned branches** `refs/heads/pilot` and `refs/heads/stable`, written with `git update-ref`: pilot = tip of its configured upstream branch, advanced after each fetch (only if the new tip is signed by a configured allowed signer — `git log -1 --format=%G?` = `G` — when `linux.allowed_signers` is set; otherwise unconditionally; a refused tip is recorded in `last_error`); stable = the promoted commit. Devices run `ansible-pull -C <ring>`: shallow clones work (ansible only honours `depth` for branches/tags — a 40-hex `-C` forces full clones), the promoted commit can never be pruned or GC'd, promotion is atomic, and `git log stable..pilot` is the candidate list. Check-in returns `{ring, revision}` where `revision` is what the ring currently resolves to (for lagging/report matching) — the agent checks out the ring, not the sha.
- Mirror config at init: `http.receivepack=false`, `http.getanyfile=false`, `http.uploadarchive=false`, `pack.threads=1`, `gpg.format=ssh`, `gpg.ssh.allowedSignersFile=$LINUX_GIT_DIR/allowed_signers`. No custom gc/repack: measured server CPU for a full clone of a config-sized mirror is ~20 ms and 100 simultaneous clones finish in ~4 s (pack reuse), so git's defaults are enough; the 2-week prune grace already protects in-flight fetches.
- Storage: **named volume** `git_mirror:/app/data/git` in both compose files; `/app/data/git` added to the existing `mkdir … && chown -R node:node /app/data` line in both Dockerfiles (a separate later `mkdir` would leave it root-owned). Clone/fetch always run **after** `listen()`; explicit state `absent|cloning|ready|stale|error` — while not `ready`, check-in returns `git: null, retry_after_s` (agent skips the cycle without reporting) and the smart-HTTP routes answer 503 + Retry-After. Upstream URL change = `git remote set-url upstream <new>` + fetch (no temp-dir rename: `rename()` onto a non-empty dir fails). Boot never contacts upstream when the volume holds a mirror.
- Every git child: `spawn(..., {detached:true})`, explicit minimal env (`PATH, HOME, GIT_TERMINAL_PROMPT=0, GIT_HTTP_LOW_SPEED_LIMIT=1000, GIT_HTTP_LOW_SPEED_TIME=60` + the credential helper vars — never `process.env`, which holds DATABASE_URL etc.), deadline (fetch 300 s, clone 900 s, log/rev-parse 30 s) enforced with `process.kill(-pid, 'SIGKILL')` (process group — a plain `child.kill()` orphans `git-remote-https`, which lives forever with node as PID 1); `stopWorkers` kills the child instead of awaiting it; `last_error`, `fetch_age_s`, child count exposed by `/git/status`; stale mirror (> 3× cadence) raises through the existing alerts route.
- Image: `RUN apk add --no-cache git git-daemon openssh-keygen` **before `USER node` in both Dockerfiles** (`git-http-backend` lives in Alpine's `git-daemon`, `ssh-keygen` in `openssh-keygen`; Ubuntu CI runners have both inside `git`, so runner-only tests would pass while prod 500s). Boot self-check: `$(git --exec-path)/git-http-backend` exists and `ssh-keygen` resolves, else mirror state `unavailable` (never per-request 500s). CI `validate-docker-build` asserts both binaries in the built image.

Pull-managed rows: `ip_netbird` NULL, `agent_version` NULL (the Linux agent version lives on the key row — keeps them out of the Windows version panel and the `agent_seen_recent` rule), `source` untouched. Check-in writes `last_seen`, `os`, `disk_used_pct` only.

## 3. Enrolment, approval, conversion (the OOBE contract)

**`POST /api/linux/agent/enroll`** {serial, hostname, os_version, agent_version, key_backing, public_key} — signed by the new key; idempotent; IP-only limit 30/min; body ≤ 4 KiB.
- Unknown key → insert `pending` (capped: if `count(status='pending') ≥ 500` → 429 + audit `linux_enroll_flood`; re-contacts of existing keys are never blocked).
- If the normalized serial matches a **pre-registration** and matches **no** existing `devices` row and no approved key → auto-approve inline: new `devices` row (platform linux, managed_by pull, profile/ring/assigned_user from the pre-registration, hostname per §4 rule), pre-registration consumed, audit `linux_device_enrolled` (source preregistration). **Auto-approve never touches an existing row.**
- If the serial matches an existing `devices` row (any platform) or an approved key → stays `pending` with `conflict={device_id|key_id, kind:'existing_device'|'reimage'|'clone'}`, pre-registration *not* consumed, audit warn `linux_enroll_serial_conflict`. The queue shows the match ("ré-image de PC-DUPONT, dernier contact …").
- Responses: `202 {status:'pending', code:<fp[:8]>, retry_after_s}` (the agent displays the 8-char code on the console/OOBE screen so an admin can find it in the queue by phone), `200 {status:'approved', device_id, hostname}`, `403 {status:'rejected'|'revoked'}`. An approved key enrolling with a *different* normalized serial → `403 {code:'SERIAL_MISMATCH'}` + audit warn.

**Approval** (`POST /api/linux/enrollments/:id/approve` {profile, ring, hostname?, assigned_user_id?, convert_device_id?, revoke_active_token?, supersede?}, `requireInteractive`):
- New device: INSERT `devices` (hostname per rule), bind key, audit `linux_device_approved`.
- `convert_device_id` (serial must match, row is Windows/legacy): **conversion** in one transaction — `platform='linux', managed_by='pull', hostname per rule (default: keep the existing one)`, `assigned_user_id = COALESCE(body/prereg value, existing)`, `clearWindowsFacts()` (DELETE compliance_results / disks / network_interfaces / device_software; NULL health_signals, health_updated_at, system_info, ssh_host_key_fp, ssh_host_key_learned_at, ip_netbird, agent_version, intune_*, compliance_state, enrolled_at, last_seen_ws; `UPDATE agent_tokens SET revoked_at=now()`; `agentWs.evictDevice` after COMMIT). If the row has an active used legacy token, refuse `409 {code:'ACTIVE_TOKEN'}` unless `revoke_active_token:true` (mirrors device-claim.js posture). Audit `linux_device_converted` with the cleared counts. Ticket/stock/group history is kept (group_members is keyed by device_id).
- Existing **pull** row with the same serial (re-image / lost key): refuse `409 {code:'ACTIVE_KEY', old_key, hostname, last_seen_at}` while another key is approved for it, unless `supersede:true` (revokes the old key `revoke_reason='superseded'` in the same transaction); then rebind to the existing row, audit `linux_device_reenrolled`.
- Hostname rule (`resolveHostname`, pure, unit-tested): explicit body > pre-registration.hostname > existing row's hostname (conversion/re-enrol) > `lx-<normalizedSerial>` > `lx-<fp[:12]>`. Never the agent's claim. All hostnames of a batch are resolved and checked (against `devices` and within the batch) before BEGIN; collisions return per-row `HOSTNAME_TAKEN`; 23505 inside the transaction still maps to 409.
- `approve-bulk {ids, profile, ring}` → `{approved, skipped, errors:[{id, code}]}`; `reject-bulk {ids}`; `reject/:id`.

**Pre-registrations**: `POST /preregistrations` (JSON rows; the UI parses pasted CSV `serial,hostname,profile,ring,email` client-side and also offers a single-row form), per-row validation and errors; `POST /preregistrations/from-devices {device_ids|group_id, profile, ring}` — the **migration primary flow**: from Postes, select Windows laptops → "Préparer la migration Linux" → pre-registrations with their serial/hostname/user; on first boot of the re-imaged laptop the serial matches an existing row so it lands in the queue as `reimage`/`existing_device` and the admin converts it with one click (auto-conversion is deliberately not automatic: conversion mutates a live row).

**`DELETE /api/devices/:id`** (inventory) additionally shows, in the confirm, the number of escrowed recovery keys that will be destroyed.

## 4. Agent API (`/api/linux/agent`, signed unless noted, schemas from the spec)

| Op | Purpose |
|---|---|
| `POST /enroll` | §3 |
| `POST /checkin` {serial, agent_version, os_version, hostname, kernel, uptime_s, disk_root_pct?, luks_root: bool, escrow_key_id?} | Serial re-check (mismatch → `403 SERIAL_MISMATCH` + audit warn throttled 1/h per key; NULL/fake `serial_claimed` adopts the first real serial). Writes `devices.last_seen/os/disk_used_pct`, key row `last_seen_at/agent_version/os_version`. Returns the **assignment**: `{device_id, hostname, profile, ring, revision (40-hex the ring resolves to, informational), git:{url, token, token_expires_at} | null (mirror not ready → plus retry_after_s), escrow:{status:'ok'|'unavailable'|'backup_unconfirmed', public_key_pem, key_id}, escrow_needed:[...], local_admin_username, rotate_local_admin: bool, checkin_interval_s: 900, extra_vars:{opale_profile, opale_ring, opale_device_id, opale_hostname}}`. If the git stage fails: sleep 30 s, re-check-in (fresh token), retry once, then report `failed`. Playbooks target `hosts: localhost` + `connection: local`; roles vendored in the repo (ansible-pull never runs galaxy); "no hosts matched" is reported as `skipped`. Per-device limit 12/h. |
| `POST /reports` {revision, status, started_at, finished_at, error_summary, log_tail} | Append (log_tail dropped when status=success; `skipped` = `--only-if-changed` no-op, no log); update `devices.last_*`; audit on transition only (`linux_apply_failed`, `linux_apply_recovered`); when `linux.alerts_enabled`: push to admins (`url:/mobile.html#/poste/<id>`, which renders pull rows read-only after PR 2) + idempotent `ticket_proposal` (compliance precedent) + system event on the device's open tickets. 12/h per device. |
| `POST /escrow` {kind:'local_admin', username, ciphertext, rotated_at} \| {kind:'luks_recovery', label, ciphertext} | local_admin: `username` must equal `local_admin_username`; `rotated_at` must be > stored `password_changed_at` (replay guard); upsert `device_admin_credentials` (existing reveal route/UI); clears `rotation_requested_at`; audit `laps_rotated` (existing action, `by_user='device:<fp12>'`). luks: INSERT `device_recovery_keys` with `key_id`, previous row with same label → `superseded_at`; audit `linux_recovery_key_escrowed`. Ciphertext = RSA-OAEP-SHA256 to `escrow.public_key_pem`, 200..1024 B; plaintext ≤ 150 B agent-side. 6/min per device. |
| `GET /git/fleet.git/info/refs?service=git-upload-pack` and `POST /git/fleet.git/git-upload-pack` (NOT signed; exactly these two routes, no wildcard) | `Authorization: Bearer <git.token>` — 10-min token minted at check-in, bound to device_id, sha256-hashed in a RAM store with TTL (`lib/git-token-store.js`: create/verify/revokeDevice, unit-tested); each request also re-checks the key row is still `approved` (one indexed SELECT) so revoke is instant. Spawns `git http-backend` (git owns HTTP framing, protocol v0/v1/v2 advertisement and **gzip request inflation** — git gzips every fetch POST > 1 KiB; a direct `upload-pack` spawn would have to re-implement all of that) with an explicit env allowlist: `PATH, HOME, GIT_PROJECT_ROOT, GIT_HTTP_EXPORT_ALL=1, REQUEST_METHOD, PATH_INFO` (fixed per route, never from input), `QUERY_STRING, CONTENT_TYPE, HTTP_CONTENT_ENCODING, HTTP_GIT_PROTOCOL`, `CONTENT_LENGTH` only when the header is present (chunked bodies read to EOF); no `REMOTE_USER` (it would enable receive-pack). Content-type parser for `application/x-git-upload-pack-request` hands the raw stream to the child (without it Fastify answers 415 before the handler; git gzips negotiation bodies > 1 KiB and http-backend inflates them itself when `HTTP_CONTENT_ENCODING` is forwarded — never gunzip in Node); own byte counter (4 MiB → 413) because Fastify's `bodyLimit` does not apply to passthrough parsers. CGI response parsed by `lib/cgi-response.js` (pure, unit-tested: `Status:` line may follow other headers; delimiter split across chunks; premature EOF → 500). Child lifecycle is the real leak to prevent: `req.raw.on('close') → child.kill('SIGKILL')` and a 5-min hard timer per child; a small semaphore (8 concurrent spawns, beyond → 503 + `Retry-After: 30`) is insurance against one abusive device, not fleet load (measured: 100 simultaneous full clones ≈ 4 s server-side). `info/refs` with any other `service` → 403; `GET /HEAD`, `/objects/*`, `POST /git-receive-pack` → 404 (never routed). 30/min per device. |

Escrow key: `escrow.public_key_pem` is **derived** (`crypto.createPublicKey(loadLAPSKey()).export({type:'spki',format:'pem'})`, memoised; `loadLAPSKey` moved to `api/modules/inventory/lib/laps-key.js`, shared with the reveal route; `laps.pub` is never read by the API). Unreadable key → `escrow.status='unavailable'`, check-in still succeeds, agent skips escrow, admin `GET /api/linux/escrow/status` and a "non escrowé" filter/KPI surface it (`luks_root AND no current recovery row`, or `key_id ≠ current`). `escrow_needed` tells the agent what to (re-)escrow after a key change or a device re-creation.

The agent never receives commands, scripts, packages or binaries. Agent self-update is the image/apt repo's job.

## 9. Decisions

Decided (say so if you disagree): Ed25519 signed requests; shared `devices` table with `managed_by` + existing views made platform-aware; pending rows outside `devices`; Opale git mirror + pinned revision per ring; trust root on the device; escrow key derived from `laps.key`; local admin username = `agent.laps_recovery_username`; recovery keys cascade on device delete (revoke keeps them); no new mobile screens in v1; profiles = files in the repo.

Decided by the user (2026-09-30):
1. **Least privilege v1**: `requireInteractive` on approve/reject/revoke, settings, promote, git sync, both reveal routes. CLI tokens get `403 {code:'INTERACTIVE_ONLY'}` there.
2. **LAPS reveal for Windows**: upgraded to `POST /api/admin-credentials/:device_id/reveal {reason}` + fail-closed audit for **all** devices (GET removed; front/api.js, poste.js, mobile/poste.js, demo/api.js, route test updated; the LAPS modal reuses the SSH/console reason picker).
3. **`laps.key` backup**: no off-box copy exists today. Gate: `POST /api/linux/agent/escrow {kind:'luks_recovery'}` answers `409 {code:'ESCROW_BACKUP_UNCONFIRMED'}` (agent retries next check-in; `escrow.status='backup_unconfirmed'` in the assignment tells it not to bother) until an admin confirms `linux.escrow_backup_confirmed` in Paramètres (one-time ★ action, audited `linux_escrow_backup_confirmed` with the actor; the setting is cleared automatically if the served `key_id` changes). INSTALL/UPGRADING get the backup procedure (copy laps.key off-host encrypted, `openssl rsa -check`, first-reveal proof). Local-admin escrow is not gated (the agent can always regenerate that password).
4. **Pre-registration auto-approve**: kept, brand-new hardware only; any serial matching an existing device or approved key goes to the queue with the conflict shown.
